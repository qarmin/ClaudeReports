Baseline (library's own compile, external linkage, ordinary calling convention):
  define void @_RNvXsd_..._DynamicImage...GenericImage9put_pixel(...) unnamed_addr #0
  attributes #0 = { nonlazybind uwtable "probe-stack"="inline-asm" "target-cpu"="x86-64" }

Patched (per-consuming-crate compile, triggered by #[inline]):
  define internal fastcc void @_RNvXsd_..._DynamicImage...GenericImage9put_pixel(...) unnamed_addr #3
  attributes #3 = { inlinehint nonlazybind uwtable "probe-stack"="inline-asm" "target-cpu"="x86-64" }

Everything else in the function body (every instruction opcode, every basic block, the full
908-line body including all 12 match-arm blocks) is textually identical between the two variants
after normalizing crate-hash-derived symbol suffixes and !metadata node numbers (both artifacts
of compiling in two different LLVM modules, not of any semantic difference) - confirmed via
`diff` on the two full function bodies. The only real differences at the LLVM-IR level are:
linkage (external -> internal), calling convention (ccc -> fastcc), and the added `inlinehint`
function attribute - all three are direct, simultaneous consequences of adding `#[inline]` to
`put_pixel`'s definition, not something introduced by any Rust/LLVM middle-end optimization pass
touching the function body's own instructions.
