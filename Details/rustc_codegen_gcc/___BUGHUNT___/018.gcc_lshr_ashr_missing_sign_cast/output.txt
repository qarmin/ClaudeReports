=== Root-cause instrumentation (temporary, added then reverted during investigation) ===

Debug eprintln! added to Builder::ptrtoint/bitcast/inttoptr and Builder::gcc_lshr, compiling the
original minimal repro, showed the exact type mismatch:

DEBUG inttoptr: value_type=__int64_t  __attribute__((aligned(8))) dest_ty=__int8_t *
DEBUG ptrtoint: value_type=__int8_t * dest_ty=__int64_t  __attribute__((aligned(8)))
DEBUG gcc_lshr: a_type=__int64_t  __attribute__((aligned(8))) a_type.is_signed=true b_type=__int64_t  __attribute__((aligned(8)))
DEBUG bitcast: value_type=__int8_t[8]  __attribute__((aligned(8))) * dest_ty=__int64_t  __attribute__((aligned(8))) *
DEBUG ptrtoint: value_type=__int8_t * dest_ty=__uint64_t  __attribute__((aligned(8)))
DEBUG gcc_lshr: a_type=__uint64_t  __attribute__((aligned(8))) a_type.is_signed=false b_type=__uint64_t  __attribute__((aligned(8)))

The transmute path's `ptrtoint` call is given dest_ty=__int64_t (signed) instead of the correct
unsigned `usize` GCC type, so the resulting value that reaches `gcc_lshr` for `u >> 2` is declared
signed even though `u` is a `usize` - GCC's native `>>` then performs an arithmetic shift instead
of the required logical one. The direct `(ptr as usize) >> 2` cast's own `ptrtoint` call, by
contrast, is given the correct dest_ty=__uint64_t, so it shifts correctly. This instrumentation was
reverted before writing the final patch; the shipped fix in patch.diff does not rely on trusting
`ptrtoint`'s destination type at all - it forces the correct sign directly inside `lshr`/`ashr`
themselves, so it also covers any other path (not just transmute) that could hand a
wrongly-signed-but-same-width operand to a shift.
