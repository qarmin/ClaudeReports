=== Manual verification that vello's gradient_p2_skewed (167) rendering is spec-correct ===

$ python3 -c "
from fontTools.ttLib import TTFont
f = TTFont('examples/assets/colr_test_glyphs/test_glyphs-glyf_colr_1.ttf')
colr = f['COLR']; table = colr.table
name = 'gradient_p2_skewed'
for bg in table.BaseGlyphList.BaseGlyphPaintRecord:
    if bg.BaseGlyph == name:
        print(bg.Paint.Format, bg.Paint.Paint.Format, bg.Paint.Paint.x0, bg.Paint.Paint.y0,
              bg.Paint.Paint.x1, bg.Paint.Paint.y1, bg.Paint.Paint.x2, bg.Paint.Paint.y2)
"
10 4 100 950 2300 950 -1000 250
# i.e. raw COLR PaintLinearGradient: p0=(100,950) p1=(2300,950) p2=(-1000,250)

Applying the OpenType COLR "rotating and skewing gradients" normalization by hand
(the same one skrifa/fontations implements, see skrifa-0.44.0/src/color/mod.rs's
`Brush::LinearGradient` doc comment: "normalized from the P0, P1 and P2 representation ... to a
linear gradient between two points p0 and p1"):

  p0p1 = p1 - p0 = (2200, 0)
  p0p2 = p2 - p0 = (-1100, -700)
  s = dot(p0p2, p0p1) / dot(p0p1, p0p1) = -2,420,000 / 4,840,000 = -0.5
  perpendicular = p0p2 - s * p0p1 = (-1100, -700) - (-0.5)*(2200, 0) = (0, -700)
  new_p1 = p1 + perpendicular = (2300, 950) + (0, -700) = (2300, 250)

So the spec-correct gradient runs from (100, 950) to (2300, 250) - a DIAGONAL line, not the
horizontal (100,950)->(2300,950) line resvg's own (documented-incomplete) implementation draws.
vello's diagonal red -> blue -> yellow rendering matches this hand-derived spec-correct result;
resvg's plain horizontal red -> blue rendering does not. Confirms vello is correct here and resvg's
own acknowledged "TODO: we ignore x2, y2" gap (usvg-0.46.0/src/text/colr.rs line 125-126) is the
actual explanation for the divergence.
