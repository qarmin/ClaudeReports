=== Supplementary evidence: instrumented build showing the internal mechanism ===
Temporarily added `eprintln!` to `two_point_linear` in the working checkout (kurbo/src/expand.rs,
reverted afterwards - not part of the shipped repro) to observe the actual per-sample values for
the single collinear headline case (cusp at t=0.35, q0=q2=(1,0)):

DEBUG two_point_linear s0=TwoPointSample { a_n: NaN, b_n: NaN, c_n: NaN } s1=TwoPointSample { a_n: 0.0, b_n: 0.0, c_n: 0.0 } det=NaN
DEBUG two_point_linear soln=None p1xp0=-0 p2xp1=0
expanded path: BezPath([MoveTo((0.0, 1.0)), LineTo((0.2673992673992674, 1.0)), LineTo((-0.7326007326007327, 0.0)), LineTo((-0.7326007326007327, 1.0)), LineTo((0.2673992673992674, 0.0)), LineTo((0.0, 0.0)), LineTo((1.0, 1.0)), LineTo((1.0, 0.0)), LineTo((0.0, 1.0)), ClosePath])

This confirms directly: the t=0.35 sample (s0) really did produce all-NaN a_n/b_n/c_n internally
(i.e. `normalize()` really did divide 0.0/0.0 there), but `det` (computed from s0.a_n/s0.b_n and
s1.a_n/s1.b_n) became NaN as a consequence, and `two_point_linear`'s own explicit check
(`det.abs().partial_cmp(&1e-12) != Some(Ordering::Greater)`, which treats an unordered/NaN
comparison as failure) caught it and returned `None`, so `do_cubic` fell back to `do_line(p3)`
instead of emitting the NaN control points into the output.
