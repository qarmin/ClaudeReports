# Optimization results

Ported on 2026-08-23 from `perf_test/___OPTIMIZATIONS___/SUMMARY.md` (an earlier session using the
predecessor `perf-optimize` workflow) into this repo-root workspace, in the current skill's
facts-only format (no `win`/`null`/`applied` verdict labels - see `~/.claude/skills/perf-optimize/SKILL.md`).
`perf_test/` itself was left untouched during the initial port; its own `___OPTIMIZATIONS___/`
remains the fuller original source (extra planning/correction notes, its own justfile and
`tools/`). It **was** touched during the 2026-08-23 re-verification pass below - two build fixes,
unrelated to any candidate's patch, needed to make it build against a clean tree at all (see
candidate `014.DEPENDENCY_NODE_RECYCLING`'s "Reproducibility check" section for what and why).
This table restates the
same 48 optimization candidates (plus the harness-building one, folded into `README.md` - see
below) for the new format and location. Numbering mirrors the original perf_test candidate
numbers (001-048) for cross-reference, not this skill's usual "start a fresh workspace at 001"
default.

**Re-verified against updated `slint`/`femtovg` on 2026-08-23** (both pulled to latest upstream `master`: slint `cdb6c43f7`, femtovg `df54a3c8`). Of the 12 patched candidates: 7 still apply cleanly with no changes (008, 011, 014, 019, 029, 041, and femtovg's half of 006); 001's two patches remain untestable this way (still target untracked `perf_test/`); 5 no longer apply as-is (003, slint's half of 006, 009, 010, 023) - each investigated to confirm the underlying issue still exists rather than assuming a stale patch means an obsolete finding (it didn't, in every case checked - see each candidate's own "Reproducibility check" section). Candidate 014 was additionally rebuilt and re-benched end to end as a concrete test of the workflow itself (-31.2%, 9/9 paired), not just an apply-check.

The harness for all of these is `perf_test/` (untouched, not duplicated) - see `README.md` in
this folder for how it's invoked, including the instrumentation that was originally its own
"candidate 00" folder (folded into `README.md` instead - it's not an optimization).

**Impact** (derived from the Result column, for scanning at a glance - not a recommendation, see `~/.claude/skills/perf-optimize/SKILL.md`'s "no verdict labels" rule, this classifies the measured magnitude/direction only): **Strong win** (large, confirmed improvement) - **Small win** (real but modest improvement) - **No change** (null result / within noise) - **Mixed** (improves one thing, regresses another) - **Small/Strong regression** (would make things worse) - **N/A** (pure measurement/characterization, no patch compared against a baseline).

**This table is code changes to Slint (or a vendored dependency) only.** Candidates whose finding
is an app-level `.slint` authoring pattern - a way to *write your own UI* faster, with no change to
the Slint engine itself - are deliberately not listed here, even when they measured a large number:
they didn't optimize the library, they demonstrated how a row/scene can be structured in the test
harness. Their own folder/`RESULT.md` still exists and is still accurate; they're just not
"optimization results" in the sense this table tracks. Excluded on this basis: `001` (row
structure), `013` (off-screen row relayout - a `ListView`-vs-plain-`for` finding), `044` (`clip:
true` on a row). `022`/`043` (model-prepend findings) were already `N/A` here for the same
underlying reason (an app-level design question, not an engine fix) and needed no change.
