# 98 - Port candidate 070's font-metrics NoWrap-height fast path to `TextInput::layout_info`

`IDEAS.md` (candidate 070 follow-up, 2026-08-24) asked whether candidate 070's fix - computing a
`NoWrap` `Text`'s `Orientation::Vertical` height from font metrics instead of shaping the whole
paragraph through parley - also applies to `TextInputItem`'s own, separate `layout_info`
implementation (`internal/core/items/text.rs`), left out of candidate 070's scope. A fixed-width
single-line `TextInput` (a search box, a form field) inside a `VerticalLayout` hits the same shape.

## The fix

`TextInput::layout_info`'s `Orientation::Vertical` / `TextWrap::NoWrap` arm: for text with no
`\n`, compute the height from `font_metrics()` instead of calling `text_size()` (which shapes the
whole paragraph through parley). Falls back to the original shaping call for any text containing
`\n`. Unlike candidate 070's version for `Text`/`SimpleText`/`ComplexText`/`StyledTextItem`,
there is no `PlainOrStyledText::Styled` case to exclude: `TextInput::text()` (via `RenderString`)
always returns `PlainOrStyledText::Plain` - `TextInput` has no rich-text/markdown support.

One implementation wrinkle not present in candidate 070's version: `self.text()` inside
`TextInput::layout_info` resolves to the *inherited property accessor* (`Property<SharedString>`,
generated by `#[derive(SlintElement)]`) rather than the `RenderString::text()` trait method,
because Rust's method resolution prefers an inherent method over a trait method when both exist on
a concrete type (candidate 070's version took a `Pin<&dyn RenderText>` trait object parameter, so
there was no inherent method to shadow it). Had to spell it out explicitly as
`RenderString::text(self)` to get the `PlainOrStyledText` this fast path needs (masked for a
password field, includes preedit) instead of the raw `text` property.

## How the fast path's actual effect was confirmed (and why it's smaller than candidate 070's)

Added temporary atomic counters (removed before finalizing `patch.diff`) to
`TextInput::layout_info`, counting `Orientation::Horizontal` vs `Orientation::Vertical` calls and
which arm (`font_metrics` fast path vs `text_size` fallback) each `Vertical` call took, run against
`perf_test`'s `scroll` mode with a new `RowStyle.vertical-fixed-input` scene (`VerticalLayout` of 3
fixed-width, `NoWrap` `TextInput`s per row - the `TextInput` counterpart of candidate 070's
`vertical-fixed` `Text` scene). At `--count 2000` (6000 `TextInput`s): `H=1 V=6001`, all 6001
`Vertical` calls took the font-metrics fast path (`FAST=6001 SLOW=0`) - confirms `Orientation::
Horizontal` is (as expected, symmetric to candidate 070's finding) essentially never queried for a
fixed-width `TextInput` in a `VerticalLayout`, and the fast path is reached for every one of them.

Despite that, the harness's `text shapes` counter (`TextLayoutCache::cache_miss_count()`) stayed at
**6027 regardless of whether the fast path was enabled or force-disabled** (verified by
temporarily short-circuiting the guard to always take the slow `text_size` path: still 6027
shapes, not ~12000). Traced this to a mechanism candidate 070's plain-`Text` case does not have:
`TextInput::init()` installs a delayed change tracker that runs `align_to_text` once for the
initial text value; `align_to_text` calls `set_cursor_position`, which unconditionally calls
`cursor_rect_for_byte_offset` (`internal/core/items/text.rs`) to compute `preferred_x_pos` -
**shaping the text once per `TextInput` instance at creation, regardless of visibility or focus**,
via a completely different call path than `layout_info`. A temporary counter in
`sharedparley::draw_text_input` also confirmed 0 render calls had happened by the point `show +
layout`'s shape count is sampled, ruling out "rendering already drew every off-screen row" as an
alternative explanation. This is a real, separate cost `TextInput` pays that `Text` does not -
recorded as a new `IDEAS.md` entry rather than fixed here (out of this candidate's scope: it is
not a `layout_info` problem and touches cursor/undo state, not just measurement).

Net effect: this fix's win is real but far smaller than candidate 070's dramatic one, because the
per-instance cursor-shape cost already populates the shaping cache for every `TextInput` (visible
or not) before `layout_info` is ever asked about it - so removing `layout_info`'s own call mostly
avoids a *cache lookup*, not a *shape*.

## What was tried

Bench: `perf_test`'s `scroll` mode (non-virtualized `for`, matching candidate 070's methodology),
new `RowStyle.vertical-fixed-input`. `--mode scroll --row-style vertical-fixed-input --count
20000`, measuring the `show + layout` line (the one-time initial layout pass, `--frames 3`).

| Variant | `show + layout`, single-core (`taskset -c 2`) | `show + layout`, multi-core (unpinned) | notes |
|---|---|---|---|
| baseline | 694.51 ms median (9/9 paired); repeat run 683.06 ms median (9/9) | 686.73 ms median (9/9 paired) | 60 027 text shapes, 2 798 742 allocations at `--count 20000` |
| patched | 657.44 ms median; repeat run 646.59 ms median (9/9) | 646.48 ms median (9/9 paired) | same 60 027 text shapes (see above), 2 438 742 allocations |

Single-core: **-5.3%** (694.51ms -> 657.44ms) and **-5.4%** on a repeat run (683.06ms ->
646.59ms), both 9/9 paired (`tools/paired.sh`-style alternating A/B runs, adapted to parse the
`show + layout` line instead of `later frames`). Multi-core (unpinned): **-5.9%** (686.73ms ->
646.48ms), 9/9 paired. `first frame`/`later frames` (steady-state scrolling after the initial
layout pass) unaffected either way, matching candidate 070's own finding: the fix only removes
work done once, during the initial layout pass.

Allocations during `show + layout` at `--count 20000`: baseline 2 798 742, patched 2 438 742
(**-12.9%**). Resident memory after the last frame: 371.8 MB -> 355.3 MB (**-4.4%**).

## Result

**-5.3% to -5.9%** on `perf_test`'s `scroll --row-style vertical-fixed-input --count 20000`
initial `show + layout` time, decisive (9/9 paired both single- and multi-core, reproduced on a
single-core repeat run), but a fraction of candidate 070's ~82% win on the equivalent `Text` scene
- because (see above) a separate, unrelated per-`TextInput` cost (`align_to_text`'s one-time
cursor-position shape at creation) already dominates and is unaffected by this patch. Allocations
during the same phase drop 12.9%.

## Does it change behavior/output?

- **Bit-exact?** Yes. `tools/pixelcheck.sh`, `RUNS=6`: `scroll --row-style vertical-fixed-input`
  (0 px outside the noise floor), plus 3 pre-existing scenes re-checked for regressions
  (`scroll --row-style vertical-fixed` [`Text`, untouched by this patch], `list`, `text`) - all 0
  px outside the noise floor. A dedicated standalone probe (`probe/textinput_probe.rs`, FNV-1a
  pixel hash of a window rendering every styling variant candidate 070 checked
  [size/weight/italic/family/script/emoji/letter-spacing/empty-string], the `\n` guard case, plus
  two `TextInput`-specific cases candidate 070 didn't need - `input-type: password` (masks the
  text before measuring; the fast path reads the already-masked `RenderString::text()`, so this
  checks the mask doesn't throw off the guard or the metrics) and `single-line: true`) produced
  the identical hash (`ca383481080b0548`) built against baseline and patched `i-slint-core`.
- **Is this a breaking change?** No public API or file format changes. Same theoretical caveat as
  candidate 070: `font_metrics()` is now also load-bearing for `TextInput` layout under `NoWrap`,
  not just the public `Text.font-metrics`-style accessor. Untestable for third-party `Renderer`
  implementations from this repo; all three built-in renderers share the `shared-parley` default
  and were confirmed correct via the probe.
- Project test suite: `cargo test -p i-slint-core` (default features: `std`, `unicode`,
  `shared-parley`) - 307 + 71 + 1 = 379 passed, 0 failed, 11 ignored, both before and after
  (identical). `cargo test -p slint` - all suites passed (unchanged) both before and after.
  `cargo test` in `tests/driver/interpreter` (`test-driver-interpreter`, covers every
  `tests/cases/**/*.slint` fixture including `test_interpreter_widgets_textedit_*` and every
  `tests/cases/layout/*.slint` case) - **858 passed, 0 failed** both before and after (identical).
  Note: `cargo build -p i-slint-core --all-features` fails in this environment on a **pristine**
  tree too (a `zeno` build error, `no method named 'sqrt'/'powf' found for f32'`, from an
  unrelated `--all-features` feature-graph gap that activates `i-slint-renderer-software`'s
  `path` feature - which depends on `zeno` - without also activating `zeno`'s own `std`/`libm`
  feature); confirmed pre-existing and unrelated to this patch by reproducing it with
  `internal/core/items/text.rs` stashed back to its original state. Used the default-feature test
  command instead; see `IDEAS.md` for a follow-up note.

## Why the result looks the way it does

Same mechanism candidate 070 found for `Text`: a `VerticalLayout` unconditionally asks every fixed-
width child for `Orientation::Vertical` layout info regardless of whether the answer changes
anything, and `TextInput`'s `NoWrap` branch used to always call the same shaping-backed
`text_size()` the `Horizontal` branch uses - confirmed still true for `TextInput` (`H=1 V=6001`,
`FAST=6001` once patched). The reason the *measured* win is much smaller than 070's is not that the
fix is wrong or partial - it's that `TextInput` (unlike plain `Text`) already shapes every instance
once at creation for an unrelated reason (initial cursor positioning via `align_to_text` ->
`set_cursor_position` -> `cursor_rect_for_byte_offset`), so the shaping cache is already warm by
the time `layout_info` would otherwise have populated it. Removing `layout_info`'s own call still
saves the lookup/allocation overhead (-12.9% allocations) and a real, if smaller, slice of wall
time (-5.3% to -5.9%), but not the shape itself.

## What's not done / open questions

- **New, unrelated finding, not fixed here**: `TextInput::init()`'s `align_to_text` ->
  `set_cursor_position` path shapes every `TextInput` instance once at creation regardless of
  visibility or focus - a materially larger cost than anything `layout_info` does for this scene
  (60 027 shapes vs. the ~6000 `layout_info` would have added if unpatched). Recorded as a new
  `IDEAS.md` entry; not attempted here because it touches cursor/undo-stack initialization
  semantics, not just a measurement function, and deserves its own investigation into whether the
  initial cursor-position computation can be deferred until the item is actually focused or first
  rendered.
- Not extended to any other `TextInput`-hosting widget beyond what `tests/driver/interpreter`
  already exercises (`TextEdit`'s `word-wrap` default path is untouched by this patch, same
  exclusion candidate 070 applied to plain `Text`'s `WordWrap`/`CharWrap` branches).
- Real-hardware GPU-backed renderer confirmation (femtovg/skia via `--frames`) not done this
  session - only the headless `--bench` software-renderer path was measured, matching candidate
  070's own stated scope limitation (still an open `IDEAS.md` item from that candidate too).
- `cargo build -p i-slint-core --all-features` remains broken in this environment independent of
  this patch (see test-suite note above) - not investigated further as it is unrelated to this
  candidate's change.
