# 42 - what decoding an image costs, and why the format ranking is a trap

Ported from `perf_test/___OPTIMIZATIONS___/42_decode_cost/RESULT.md` on 2026-08-23 (original perf_test-relative session; source and any extra notes remain there untouched).

Nothing here had ever decoded a real file: `--mode images` generated its RGBA buffers in Rust
(candidate 016). `src/bin/image_probe.rs` now measures the decode itself.

## Throughput

| asset | 1920x1080 decode | Mpixel/s |
| --- | --- | --- |
| `large.png` (high-frequency pattern) | 15.22 ms | 136 |
| `large.jpg` (same pattern, q85) | 24.14 ms | 86 |
| `large_alpha.png` (RGBA) | 22.75 ms | 91 |
| `smooth_large.png` (gradient) | 11.62 ms | 178 |
| `smooth_large.jpg` (same gradient, q85) | **7.92 ms** | **262** |

**The ranking reverses with the content.** On the noisy pattern PNG decodes 1.6x faster than JPEG;
on the smooth one JPEG decodes 1.5x faster than PNG. Both are the same resolution and the same
decoder crate.

The reason is visible in the file sizes the same generator produced: the noisy 1080p PNG is 5.1 MB
and the smooth one 245 KB. A PNG that barely compresses is mostly `inflate` of nearly-raw bytes,
which is fast; a JPEG of high-frequency content has full DCT work to do on every block. Reverse the
content and the argument reverses with it.

**So "PNG or JPEG, which decodes faster" has no answer**, and any benchmark that reports one is
reporting its own test image. The honest statement is the range: **8 to 24 ms for a 1080p image**,
a 3x spread driven by content rather than by format.

## Two things that follow

**A single 1080p decode does not fit in a frame.** At 60 Hz the budget is 16.7 ms; the noisy PNG
takes 15.2 ms and the JPEG 24.1 ms. `Image::load_from_path` runs on the UI thread, so setting one
image source drops frames on its own.

**Combined with candidate 038, it repeats.** Any image above ~5 MB decoded is never cached and never
deduplicated, so a gallery or a model-driven thumbnail list pays these 8-24 ms **every time an image
comes back into view**, and twice over if two items show the same file.

## Small images are all fixed cost

`small.png` (64x64, 4 096 pixels) takes **0.30 ms** - a throughput of 13.7 Mpixel/s, an order of
magnitude below the large-image figures. That number is not decode speed, it is the fixed cost of
opening the file, sniffing the format and setting the decoder up. For icon-sized assets that fixed
cost is essentially the whole cost, which is the argument for an atlas or for
`@image-url(...)` embedding rather than for choosing a format.

## Method note

The assets are generated by `cargo run --bin make_assets`, which now writes **two** patterns at each
size: the high-frequency one and a smooth gradient. That was not the original plan - the first
measurement used only the noisy pattern and produced "PNG is 1.6x faster than JPEG", which is a
statement about the test image and would have been written up as a statement about the decoders.

## Reproduce

```sh
cargo run --profile rdebug --bin make_assets
cargo run --profile rdebug --bin image_probe
```
