# FEMTOVG_9SLICE_FITS_VEC

`internal/renderers/femtovg/itemrenderer.rs`'s `draw_image_impl` computed the list of `FitResult`s
to draw (one for a plain image, up to nine for a `NineSlice` border image) and
`.collect::<Vec<_>>()`ed it before looping over it, on every single frame regardless of whether
anything changed. The software renderer's equivalent site (`internal/renderers/software/lib.rs`,
`draw_image`) streams the exact same `fit9slice`/`fit` iterators directly with no intermediate
`Vec`. Flagged by a femtovg/software discovery sweep as a real, confirmed gap (not an inherent
cost of the iterator) by direct comparison to the sibling renderer doing the same job without the
allocation.

## What was tried

Replaced the `if let ... { collect::<Vec<_>>() } else { vec![...] }` + `for fit in fits` shape
with a `draw_fit` closure holding the (large) per-fit drawing body, called either via
`fit9slice(...).for_each(draw_fit)` for a `NineSlice` source or directly once for a plain image -
mirroring the software renderer's own `for fit in fit9slice(...) { self.draw_image_impl(...) }`
shape. No `Vec` is allocated on this path anymore; `fit9slice` itself is already a
`Flatten<array::IntoIter<Option<FitResult>, 9>>` with no heap allocation of its own.

`perf_test`'s `images` scene had no way to reach `ImageInner::NineSlice` at all (dynamic
tiling/crop-based tests only reach `fit`'s single-`FitResult`, non-`Vec`-allocating branch on
`main`/HEAD already since `vec![x]` still allocates but only once, not the interesting case).
Added an `--image-nine-slice` flag (`perf_test/src/backend.rs`, `bench.rs`, `main.rs`) that loads
the existing `perf_test/assets/nine_slice.png` asset (96x96, already generated by
`src/bin/make_assets.rs` in an earlier session but never wired to a scene) and calls the public
`slint::Image::set_nine_slice_edges(24, 24, 24, 24)` on it before `set_image_source` - this is a
runtime API, so no new `.slint` nine-slice literal or scene wiring was needed. See `../README.md`
for this as a permanent harness addition.

All numbers: `RUNS=9`, `tools/paired_femtovg_later_frames.sh`, median of 9 alternating runs each
side, `--renderer femtovg`, `LIBGL_ALWAYS_SOFTWARE=1 xvfb-run -s "-screen 0 1280x900x24"` (femtovg
has no headless `--bench` path). Machine: 24 cores, `uptime` load 0.7-1.3 at measurement time.

Confirmed the allocation removal itself is real and not a no-op, via the bench's own allocation
counter (`--frames 5`, `--count 200 --image-nine-slice`, steady-state frame): baseline
22188 allocations/frame -> patched 21588 allocations/frame, a drop of exactly 600 = 200 items x 3
(the `Vec`'s growth reallocations for up to 9 elements starting from `fit9slice`'s unsized
`Flatten` iterator, which doesn't report an exact `size_hint`, so `collect` grows the buffer
0->4->8->16 instead of allocating once at the right size).

## Result

No measurable change. All four baseline-vs-patched deltas (-0.3%, -1.3%, -0.0%, +1.5%) fall
inside the -0.1%..+/-1-2% noise floor measured from a same-binary (baseline-vs-baseline) run at
the same settings. The allocation reduction is real (600 fewer allocations/frame, confirmed via
the bench's allocation counter) but too small in wall-clock terms to surface against this scene's
per-frame cost, which is dominated by femtovg draw calls, path tessellation and (under
`LIBGL_ALWAYS_SOFTWARE=1`) software GL rasterization - roughly 14-40 ms/frame for 200-1000 items,
next to which ~600 allocations of a few dozen bytes each is on the order of tens of microseconds.

## Does it change behavior/output?

- **Bit-exact?** Yes. `md5sum`-identical PPM snapshots between baseline and patched binaries
  across `--image-nine-slice`, `--image-nine-slice --image-rescale`, plain (no flags), and
  `--image-tiling`, `--count 100`, `--frames 6`, under `xvfb-run` - 3 runs per side per variant,
  all byte-identical (not just outside-noise-floor identical; the femtovg `images` scene's
  `--snapshot` output for this scene had zero run-to-run noise at these settings, unlike the
  status-label noise `tools/pixelcheck.sh`'s header describes for other scenes).
- **Is this a breaking change?** No. Internal-only change to `i-slint-renderer-femtovg`; no
  public API, file format, or documented behavior changes.
- Project test suite: `i-slint-renderer-femtovg` has no unit tests to run. No other crate's tests
  touch this code path.

## Why the result looks the way it does

The candidate's premise (a real, avoidable per-frame allocation, confirmed by side-by-side
comparison with the software renderer's equivalent zero-allocation site) was correct - the `Vec`
was genuinely being allocated and reallocated (up to 3 times per `NineSlice` image) on every
frame for no reason. What the premise didn't account for is scale: this is a single small heap
allocation removed from a code path whose per-item cost is dominated by several femtovg draw
calls, path construction and (in this measurement setup) a fully software OpenGL rasterizer -
each `fit` still does a `create_image_empty`/blit or a `fill_path` regardless of whether the
`Vec` around it existed. A handful of small allocations is simply not where the time goes here,
unlike candidate `057` (a full GPU texture create+blit+destroy cycle) or `009`/`058` (allocations
that scaled with far larger element counts or ran in an actually allocation-bound path). This is
consistent with `009.GRADIENT_STOPS_VEC` and other "the iterator itself already exists, only the
`Vec` around it is new" candidates in this backlog: correctness of the observation does not imply
a measurable win once GPU/rasterization cost dominates the frame.

## What's not done / open questions

- Not tested with a much larger `--count` (e.g. 5000+) where per-frame allocator pressure might
  start to compete more with GPU cost, or under a real (non-`llvmpipe`) GPU driver where per-item
  draw-call cost is lower and a fixed per-item CPU cost like this would show up proportionally
  more. Worth a follow-up only if a future candidate needs to isolate CPU-only cost on this path
  specifically (added to `IDEAS.md`).
- The `--image-nine-slice` flag only exercises one asset/border configuration (24px borders on a
  96x96 source, `--image-distinct` not covered for nine-slice sources) - sufficient to confirm the
  correctness and allocation-count claims, not exhaustive over nine-slice configurations.
