Note: mold forks a child process to do the actual linking work (src/subprocess-unix.cc
fork_child(), "Exiting from a program with large memory usage is slow"). The crash happens in
that forked child; the parent process only sees a normal SIGSEGV-terminated child and re-raises
the same signal itself (subprocess-unix.cc:47), so `gdb --args mold ...` alone (or a plain
`mold ...` run whose stderr is captured) attaches/reports against the PARENT, not the process
that actually faulted. Reproducing needs `set follow-fork-mode child` in gdb (or, for a plain
run, just observing the exit status/signal - the parent's own re-raise still terminates the whole
process group with SIGSEGV, so `mold ...; echo $?` alone is sufficient to detect the crash even
without gdb).
