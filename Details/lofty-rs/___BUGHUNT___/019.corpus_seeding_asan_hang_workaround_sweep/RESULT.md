# corpus_seeding_asan_hang_workaround_sweep

`fuzz/fuzz_targets/*.rs`, all 19 targets - a backlog item from `IDEAS.md` (noticed while working
candidate `018`, added 2026-08-26). Candidate `018` found the default-ASAN empty-corpus hang
(first seen in candidate `009`) also hangs on `mp4file_read_from`/`flacfile_read_from`, and one
control run with a leftover 23-29-file corpus on `mp4file_read_from` avoided the hang - but that
was checked only once, on one target, with a corpus much bigger than "one file". This candidate
sweeps whether seeding `fuzz/corpus/<target>/` with exactly one file reliably avoids the hang
across every target, as the backlog item asked, to decide whether it's solid enough to replace
`README.md`'s blanket `--sanitizer none` guidance.

This is a tooling/environment finding, not a bug in `lofty`'s own source - no lofty source file
was suspected or touched.

## What was tried

| Approach/tool | Config (build/input/duration) | Outcome |
|---|---|---|

Combined with the sweep's own run: **6/6 hangs total on `mp4file_read_from`** across 3 different single-file seeds. |

## Status

**Confirmed** (that the backlog item's hypothesis - "seeding with even one file reliably avoids
the hang" - is false, not merely unconfirmed). Reproduction rate: the *hang* reproduces 17/18
hanging targets with a 1-file seed present (only `speexfile_read_from` was fixed by it), and on
`mp4file_read_from` specifically, 6/6 independent runs across 3 different single-file seeds all
hung despite the seed. `filetype_from_buffer` never hangs regardless of corpus state (1/1 empty,
1/1 seeded).

**Fully reproducible: Yes.** Single-participant finding (the real `cargo +nightly fuzz run`
command a maintainer or a future session would actually run, against the project's own real,
already-existing fuzz target binaries) - `CONFIRMATION.md` section 11's caveat about a faked
second participant doesn't apply. `repro/run.sh` runs the exact real command end-to-end (build,
seed the corpus with one real file, run under ASAN, run the `--sanitizer none` control) and
captures the exact real hang; run twice during this session, both times reproduced.

## Class

`tooling` (environment/sandbox interaction with `cargo-fuzz`'s default ASAN sanitizer build, same
class as candidate `018` - not a defect in `lofty`'s own source).

## Root cause

Refines candidate `018`'s root cause rather than replacing it. `018` narrowed the hang to "the
first `NEW_FUNC` coverage-symbolization event when starting from an empty corpus" - phrased that
way because its only successful control run happened to also be the only run with a **large**
(23-29 file) corpus. This sweep shows the accurate trigger is narrower and less forgiving than
"non-empty corpus": it's **any run in which ASAN's libFuzzer instance encounters a code path whose
coverage it hasn't recorded yet**, regardless of whether the corpus is empty. A single seed file -
even a large, real, valid file - still drives libFuzzer's own `INITED`/`REDUCE` minimization
passes over dozens to hundreds of *derived* inputs before it's satisfied (visible in `output.txt`:
`corp: 1/1121b` shrinking through many `REDUCE` steps down to single-digit byte counts), and each
of those derived inputs is itself likely to touch at least one function ASAN's coverage map has
never symbolized before - so a 1-file seed almost always still triggers a fresh `NEW_FUNC` event
during its own first run, just a few hundred executions later than the empty-corpus case rather
than immediately. Candidate `018`'s control run avoided the hang not because "a corpus existed"
but because its 23-29 files, built up over an earlier `--sanitizer none` session, already
collectively covered enough of the binary's functions that no *new* one came up during the ASAN
pass. `speexfile_read_from` being the one exception in this sweep is consistent with this: it's
plausibly a small enough/simple enough parser that even one seed file's own coverage happens to
exhaust its reachable function set on the first pass, by chance - not because 1-file seeding is
special.

## The fix

No source fix - this is a tooling/environment finding (Confirmed only in the sense of confirming
the *earlier* candidate's proposed workaround is unreliable), not a code defect.

The practical consequence for `README.md`/`___BUGHUNT___/README.md`'s existing guidance: **do not
replace the blanket `--sanitizer none` guidance with a "seed the corpus first" workflow** - this
sweep shows that workaround only reliably avoids the hang once the corpus already provides
*near-total* coverage of the target (the scale candidate `018`'s one lucky control run happened to
have), not "one file", and a maintainer has no cheap way to know in advance how much corpus is
"enough" for a given target short of already having run a long `--sanitizer none` campaign first -
at which point ASAN's marginal benefit for that specific run is small anyway. `___BUGHUNT___/README.md`
has been updated in this session to record this (see below); no change was needed to
`lofty-rs/README.md` itself since it never carried a corpus-seeding-as-primary-workaround claim in
the first place (only `--sanitizer none` guidance, which this finding leaves unchanged).

- Project test suite: not run for this candidate (no `lofty` source files were modified; nothing
  to regress-test - `git status --porcelain=v1` showed only the untracked `___BUGHUNT___/`
  directory, confirmed both before and after this session).

## What's not done / open questions

- Only 1 seed file per target was tried in the main sweep (per the backlog item's literal
  wording, "even one file"); a systematic sweep of *how many* files are needed per target before
  the hang reliably goes away (matching candidate `018`'s lucky 23-29-file case) wasn't done -
  each target likely needs a different threshold tied to its own function count, and finding that
  threshold empirically for all 19 targets would need a much longer session.
- The `speexfile_read_from` exception (1-file seed avoided the hang there, uniquely) wasn't
  independently re-run to confirm it holds up across repeats the way `mp4file_read_from`'s hang
  was (6/6) - it's plausible but unconfirmed that it's reliably safe rather than a one-off; treat
  it as "observed once, not confirmed reliable" rather than "safe to rely on".
- The exact symbolizer-internals mechanism blocked under this sandbox (same open question
  candidate `018` left, and the same `strace`/`gdb`-equivalent access gap) is still not identified
  at the syscall level - unchanged by this candidate.
