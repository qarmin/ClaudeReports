# `Pixmap::take_unpremultiplied`: float division -> integer LUT

Also wired into hayro, see
[`../../hayro/___OPTIMIZATIONS___/003.hayro_vello_unpremultiply_wired_in/RESULT.md`](../../hayro/___OPTIMIZATIONS___/003.hayro_vello_unpremultiply_wired_in/RESULT.md).

## Why this was a target

`Pixmap::into_png()` - used by every consumer that saves a rendered page as PNG, including
hayro's `render.rs` example and its own test suite - calls `take_unpremultiplied` unconditionally
on the whole framebuffer. The original code did a scalar `f32` division per pixel
(`255.0 / f32::from(a)`), right next to a crate that otherwise vectorizes almost everything with
`fearless_simd`.

## What was tried

`patch.diff` - a 256-entry `const` 16.16 fixed-point reciprocal LUT + integer multiply/shift,
replacing the float division. No `unsafe` (`vello_common` has `#![forbid(unsafe_code)]`, same as
hayro).

## Benchmark: `bench/`

Self-contained benchmark project (own `Cargo.toml` with a real path dependency on
`vello_common` - apply `patch.diff` there and re-run to measure it):

```
cd bench
taskset -c 2 cargo run --release -- 30
```

4000x3000 premultiplied buffer, `taskset -c 2`, 30 iterations, hash-checked every iteration:

| Variant | single-core min | single-core p50 | mean |
|---|---|---|---|
| baseline (float division) | 42.78 ms | 44.16 ms | 43.82 ms |
| LUT (this patch) | 32.11 ms | 32.29 ms | 32.29 ms |

## Result

~25-27% faster in isolation on this operation.

## Does it change behavior/output?

- **Bit-exact?** no - characterized exactly. Exhaustive check over the entire *valid*
  premultiplied domain (component <= alpha, the actual `Pixmap` invariant - 32896 pairs):

  | Metric | Value |
  |---|---|
  | Pairs that differ from the float version | 161 / 32896 (0.49%) |
  | Max absolute difference | 1 (one LSB, on R/G/B only - alpha is passed through unchanged) |

- What changes, for whom: any consumer of `take_unpremultiplied`/`into_png` may see up to 1 LSB
  difference in R/G/B channels for ~0.5% of (component, alpha) combinations. Alpha itself is
  never affected.
- **Is this a breaking change?** no public API change; a pixel-value difference of the magnitude
  above wherever this function is used.
- Project test suite (`cargo test --release -p vello_sparse_tests`), before/after, separating
  pre-existing failures (238 - missing local snapshot/font assets in this checkout, present
  regardless of this change) from failures this patch causes:

  | Test suite state | Failing tests |
  |---|---|
  | Before patch | 238 |
  | After patch | 240 |
  | New failures caused by this patch | 2: `issues::gradient_color_alpha_unmul_cpu_f32_scalar`, `issues::gradient_color_alpha_unmul_cpu_multithreaded` |

  (Despite the name, "unmul" in that test refers to `InterpolationAlphaSpace::Unpremultiplied`, a
  gradient-stop-interpolation feature - unrelated to this function by name coincidence. The test
  renders a gradient sweeping through every alpha value 0-255, guaranteeing it hits some of the
  161 affected pairs.)

  Visual proof (`gradient_color_alpha_unmul_cpu_f32_scalar.png`, a [reference | diff-mask |
  actual] triptych generated by vello's own test harness): reference and actual are visually
  indistinguishable; the diff mask shows the deviation confined to 2 of 100 columns. Exact pixel
  numbers, from `gradient_color_alpha_unmul_cpu_f32_scalar.json`:

  | | Value |
  |---|---|
  | Pixels differing (of 5000 in a 100x50 image) | 100 |
  | Max difference per channel | R: 1, G: 1, B: 1, A: 0 |
  | Example: `x=16` column | target `#d5d52b2a` -> actual `#d4d42a2a` |
  | Example: `x=90` column | target `#1a1ae6e6` -> actual `#1919e5e6` |

## Why the result looks the way it does

Replacing a per-pixel float division with an integer multiply+shift against a precomputed LUT is
a standard fixed-point optimization; the 1-LSB rounding difference on ~0.5% of the domain is the
expected cost of approximating the exact float rounding with a fixed-point reciprocal.

## What's not done / open questions

vello's own 2 affected snapshot tests were not regenerated. Those are this (third-party,
linebender/vello) project's own accepted golden images - overwriting them is a call for whoever
owns that decision (you, if adopting this as a long-term local fork, or vello's maintainers if
this goes upstream as a PR), not something to do silently mid-audit.
