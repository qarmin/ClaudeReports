underflow and decode() actually succeeds end-to-end for every tile instead of erroring out after
the first one).

With ONLY candidate 012's own patch.diff applied (per-tile/per-call cap, reset every tile - NOT
this candidate's fix; decode() succeeds for every case below, no rejection, because each
individual tile's own estimate stays under the per-tile cap):

  40 tiles (316000x7900, xsiz=316000):  decode() succeeded, 6.909620465s, peak RSS ~3248.10 MB

  -> Time and peak memory both scale ~linearly with tile count, confirming candidate 012's own
     per-tile/per-call cap does NOT bound the cumulative cost across many tiles in one decode()
     call - each individual tile passes its own check (~3.9M raw_code_block_layer_estimate, just
     under the 4,000,000 cap), and the cap is re-checked (and re-satisfied) independently for
     every tile.

With THIS candidate's own patch.diff applied (cross-tile-accumulating cap, `storage.raw_code_block_layer_total`
persisting across the whole `decode()` call, only reset once per call in `DecoderContext::reset`):
  1  tile  (7900x7900):    decode() succeeded,        424.835222ms, peak RSS ~926.44 MB (unaffected - single tile alone was always fine)
  5  tiles (39500x7900):   decode() Err(ImageTooLarge), 443.328112ms, peak RSS ~941.85 MB
  20 tiles (158000x7900):  decode() Err(ImageTooLarge), 439.542741ms, peak RSS ~941.93 MB
  40 tiles (316000x7900):  decode() Err(ImageTooLarge), 423.569654ms, peak RSS ~941.96 MB

  -> Cost is now bounded to roughly "one tile's worth of work" (~424-443ms, ~940MB) regardless of
     how many additional tiles the codestream declares - the multi-tile case is rejected as soon
     as the cumulative total crosses the cap (after the 2nd tile's contribution pushes the running
     total over 4,000,000), instead of being individually re-permitted for every tile.
