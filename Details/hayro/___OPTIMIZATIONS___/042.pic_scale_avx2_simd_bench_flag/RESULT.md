# `hayro-bench`'s own `Cargo.toml` never requests hayro's `simd` feature - the "hottest function" in the profile is a benchmark artifact, and fixing it surfaces a real AVX2 correctness bug in `pic-scale`

`rustc 1.98.0 (88d9e12ae 2026-08-18)`, `cargo 1.98.0 (797e8a9bc 2026-08-05)`.

Investigates the candidate lead "`pic_scale::fixed_point_horizontal::convolve_row_handler_fixed_point_4::<u8, i32, 3>` is the single hottest function in the whole profile (11.68% self time), plus `column_handler_fixed_point` (5.56%) and `generate_weights` (0.70%) - about 18% combined, triggered from `hayro/src/image.rs`'s image-resize call into `pic-scale`."

That function (`hayro/../pic-scale/src/fixed_point_horizontal.rs`) is `#![forbid(unsafe_code)]` pure-Rust - it is the **generic scalar fallback** `pic-scale` uses whenever none of its CPU-feature-gated SIMD row handlers (SSE4.1/AVX2/NEON) are compiled in or detected. `hayro`'s own `Cargo.toml` (`hayro/Cargo.toml:26,32`) already has a `simd` feature in its `default` set that forwards to `pic-scale/sse`, `pic-scale/avx`, `pic-scale/neon`, `pic-scale/rdm` - so any normal downstream consumer of the published `hayro` crate already gets the SIMD-accelerated `pic-scale` row/column handlers by default. But `hayro-bench` (the benchmark this whole `___OPTIMIZATIONS___/` workspace has used throughout) depends on `hayro` via `hayro-bench/Cargo.toml:25`: `hayro = { workspace = true, features = ["embed-fonts", "embed-cmaps"] }` - **no `"simd"`** - combined with the workspace root's `hayro = { path = "hayro", ..., default-features = false }` (`Cargo.toml:29`), this means `hayro-bench`'s `render_bench`/`jpx_decode_bench` binaries have been built **without any of `pic-scale`'s SIMD row/column handlers** this entire time. (The very next line in the same file, `hayro-jpeg2000 = { workspace = true, features = ["std", "simd"] }`, *does* correctly request its own `simd` feature - and so does `hayro-tests/Cargo.toml:22`'s `hayro` dependency - which is why this looks like a one-line oversight specific to `hayro-bench`, not a deliberate choice.)

Confirmed directly: `nm -C target/release/render_bench | grep -i 'avx\|sse'` on the current (unpatched) `hayro-bench` binary returns **zero** `pic_scale::avx2::*`/`pic_scale::sse::*` symbols - only the generic `convolve_row_handler_fixed_point_4::<u8, i32, N>` for N in {1,3,4}. Adding `"simd"` to `hayro-bench`'s own `hayro` feature list (this candidate's one-line `patch.diff`) makes those symbols appear.

## What was tried

Single change: `hayro-bench/Cargo.toml`, `hayro = { ..., features = [..., "simd"] }` (see `patch.diff`). No change to `hayro`'s own library source (`hayro/src/image.rs` was not touched) - this is a benchmark-manifest fix that makes `hayro-bench` build the same way any normal downstream consumer of the published crate already does.

Benchmark: existing `hayro-bench render_bench --backend hayro` against `img.pdf` (the repo's own real test file, per `../README.md`), `taskset -c 2`, 300 iterations/run. Machine was heavily loaded during this session (5 sibling `___OPTIMIZATIONS___` candidates building/benching in parallel, `uptime` load average ~18 on 24 logical cores) even with the shared `build.lock` serializing the actual heavy commands, so the spread below is wider than a quiet-machine run would show - reported as median/min-of-repeats, not a single sample.

| Variant | single-core (300 iter, ms/page, 7 repeats) | multi-core (300 iter, ms/page, 2 repeats) |
|---|---|---|
| baseline (`hayro-bench` unpatched, scalar `pic-scale` fallback) | 3.547, 3.585, 3.654, 3.710 (median 3.62, min 3.547) | 3.237, 3.470 (mean 3.35) |
| patched (`"simd"` added, AVX2 `pic-scale` handlers) | 2.880, 2.888, 2.910, 3.127, 3.415, 3.496, 4.368 (median 3.13, min 2.880) | 2.996, 3.051 (mean 3.02) |

## Result

**Time.** Single-core median 3.62ms -> 3.13ms (**-13.6%**), min-of-repeats 3.547ms -> 2.880ms (**-18.8%**); multi-core mean 3.35ms -> 3.02ms (**-10%**). The patched side's spread is wider (2.880-4.368ms) purely because of parallel-sibling contention on this run (`ps` during the run showed 4 other candidates' `flock`-queued heavy commands) - even so, every patched sample from the first 4 repeats (taken back-to-back, less contention) beats every baseline sample, and even the noisiest patched samples land inside or below the baseline band. This lines up with the profile: the resize convolution the candidate lead pointed at is genuinely large (~18% of render time, `../README.md`'s `draw_image` bucket is 14.6% of encoder-agnostic `render()`), so replacing its scalar fallback with the AVX2 path removing most of that time end-to-end is expected in magnitude.

**This is not a "hayro is slow" finding.** Any real consumer of the published `hayro` crate that doesn't itself set `default-features = false` (i.e. almost everyone) already gets the AVX2 path today - `hayro`'s own `default` feature set includes `"simd"`. Only this repo's own `hayro-bench` binary, and by extension every prior candidate in this workspace that used `hayro-bench render_bench` as its end-to-end sanity check, was measuring the slower scalar path. Candidates that measured an *isolated* sub-operation via their own standalone `bench/` (not `hayro-bench`) are unaffected by this.

## Does it change behavior/output?

**Not bit-exact, and the difference found is a real bug, not a benign rounding difference - read this section before treating "add `simd`" as a free win.**

- `compare -metric AE -fuzz 0% baseline.png patched.png` on `img.pdf`'s one page (595x841): **26/500395 pixels differ** (0.0052%), **max channel deviation 255** (full-scale, not a rounding LSB). Saved: `correctness/img_pdf_baseline_no_simd.png`, `correctness/img_pdf_patched_simd_avx2.png`, `correctness/img_pdf_diff_highlight.png` (ImageMagick highlight diff).
- Root-caused to a specific small legend icon (`correctness/legend_icon_crop_baseline.png` vs `correctness/legend_icon_crop_simd_avx2_bug.png`, 4x-upscaled crop around page pixel (205,695)): a narrow **2-pixel-wide vertical strip** (x=205-206, spanning ~15 of the icon's rows) has its color **wrong**, not just off-by-a-shade - every differing pixel matches the pattern "R and G channels inverted (255-value), B and A unchanged": source `(0,0,0,255)` (black) renders as `(255,255,0,255)` (yellow); source `(255,255,255,255)` (white) renders as `(0,0,255,255)` (blue). This is a channel-corruption bug, not a resampling-quality difference.
- **Isolated to AVX2 specifically, not SSE.** Rebuilt with `hayro`'s `simd` feature edited to request only `pic-scale/sse` (dropping `pic-scale/avx`) as a one-off local investigation (not part of `patch.diff` - reverted before finishing): the resulting binary's `img.pdf` render hash is **bit-identical to the unpatched scalar baseline** (`b14c11e52c1b9b448ffecaa587ed2908` both times). Only enabling `pic-scale/avx` (this machine has AVX2, confirmed via `/proc/cpuinfo`) reproduces the bug. Not further isolated between `pic-scale`'s horizontal (`avx2::rgb_u8::convolve_horizontal_rgb_avx_row(s)_4`) vs vertical (`avx2::convolve_vertical_avx_row`) AVX handlers, or between the "4 rows at once" vs "1 row" dispatch - see "What's not done" below.
- Deterministic: re-ran the patched binary 3 times, identical output hash (`94bcd20c5a67c8d64738631e4c79f23e`) every time - rules out a data race (this build has no `pic-scale/threading` feature enabled anywhere in the workspace, so a threading race was never a likely explanation, but worth ruling out directly since AVX2 SIMD bugs can also come from unaligned/uninitialized-lane bugs that sometimes look racy).
- **Is this a breaking change?** No API/format change. It is a **latent correctness bug already present for any real `hayro` consumer on an AVX2 machine using default features** (independent of whether this candidate's `patch.diff` is ever applied) - this patch only makes `hayro-bench` observe the same behavior real consumers already get.
- Project test suite: `cargo test --release -p hayro-tests --test tests -- render` - **274 passed / 1252 failed, identical before and after this patch** (`hayro-tests` and `hayro-bench` are independent binary targets; `hayro-tests/Cargo.toml:22` already requests `hayro`'s `"simd"` feature regardless of this patch, so it cannot be affected by it either way). Checked the 1252 failures are all pre-existing `NotFound` (missing un-synced `downloads/` external corpus, documented in candidates `007`/`009`), zero `"pixel diff was"` failures - i.e. the bug above does **not** reproduce on any of the 274 tests actually runnable in this offline environment; it was only caught because `img.pdf` (not part of the `hayro-tests` corpus) was compared pixel-for-pixel directly. `hayro-bench` itself has 0 `#[test]`s (N/A).

## Why the result looks the way it does

`hayro-bench`'s manifest simply never asked for the feature its sibling line (`hayro-jpeg2000`'s `simd`) and `hayro-tests` both already ask for - a one-line inconsistency, not a deliberate benchmark configuration. Because every prior `render_bench`-based end-to-end measurement in this workspace inherited that gap, every one of them was implicitly measuring `draw_image`'s cost with the scalar `pic-scale` fallback - which is real, reproducible, and now fixed for future sessions, but also means the *absolute* end-to-end numbers in earlier candidates' tables were measuring a slower `hayro-bench` than what a real deployment sees today. The AVX2 correctness bug this uncovered would never have been noticed by only measuring `hayro-bench`, since the fix that makes the benchmark honest is exactly the same change that surfaces the bug.

## What's not done / open questions

- The AVX2 bug is confirmed and localized to one 2px-wide column of one small icon in `img.pdf`, isolated to AVX2 vs SSE, but **not yet bisected to horizontal-vs-vertical** or minimized to a standalone `pic-scale` reproduction (small synthetic RGB buffer + exact scale factor). That belongs to `___BUGHUNT___/` as its own candidate, not here - see this session's final report for the incidental-finding note; it was not written directly into `___BUGHUNT___/` from this worktree per this batch's own instructions.
- Not determined whether the same bug affects `pic-scale`'s CN=4 (RGBA) AVX2 path or only CN=3 (RGB) - `img.pdf`'s affected icon goes through the `!has_alpha` RGB branch in `hayro/src/image.rs` (`draw_image`'s `RenderImageData::Rgb(_) && !has_alpha && needs_resize` arm).
- Whether this is a bug in `pic-scale` itself (most likely, since hayro's own code around it - `hayro/src/image.rs` - is untouched by this patch and is `#![forbid(unsafe_code)]`) versus a bug in how `hayro` calls it (e.g. a buffer-size/stride assumption) was not fully ruled out; `pic-scale`'s AVX2 RGB convolution files (`avx2/rgb_u8.rs` in the vendored sibling clone `/home/rafal/Projekty/Obce/pic-scale`) are the next place to look.
- No attempt was made to fix the bug itself (out of scope for a benchmark-config candidate) - `patch.diff` only fixes `hayro-bench`'s manifest, it does not touch or work around the AVX2 bug.
