# hayro-ccitt BitReader bulk-refill

`rustc 1.98.0 (88d9e12ae 2026-08-18)`, `cargo 1.98.0`.

`BitReader::read_bit` (`hayro-ccitt/src/bit_reader.rs`) did one bounds-checked slice index plus
a shift/mask per bit, and is called once per Huffman-tree edge in `decode_run_inner`
(`hayro-ccitt/src/decode.rs`) - the hot loop for every white/black run length in a CCITT
Group 3/4 fax stream, up to ~13 calls per run for a make-up code. The candidate: replace the
per-bit bounds-checked byte load with a 64-bit left-justified bit buffer, refilled in bulk (up
to 8 bytes at a time, one bounds check per refill instead of one per bit) from `read_bit`/
`read_bits`; `peak_bits`/`align`/`byte_pos`/`at_end` keep their existing semantics unchanged
(`align` just drops the buffer and lets the next read refill, since it's called at most once per
row, never in the per-bit path).

## What was tried

No existing project benchmark reaches `hayro-ccitt` in isolation (the crate has no `bench`/
`example`, and hayro's own `render_bench` only exercises it incidentally via whichever test PDFs
happen to use CCITT images - none of the repo's own PDFs contain a large one). Built a standalone
`bench/` crate (see `bench/src/main.rs`) with two roles:

1. **Timed workload**: a synthetic Group3-1D (Modified Huffman) fax image (1728x3000, ~18% of
   runs long enough to need one or more make-up codes) generated by a from-scratch MH encoder in
   the bench itself (standard ITU-T T.4 code tables, transcribed independently of
   `state_machine.rs`'s own copy - not the code under test), decoded through the real
   `hayro_ccitt::decode` entry point.
2. **Correctness-only workload**: a deterministic 207-file/1.1 MB sample of `hayro-fuzz`'s
   `fuzz_ccitt` corpus (`bench/testdata/corpus/`, copied in - note: this corpus was seeded from
   whole test PDFs, not crafted `fuzz_ccitt` inputs, so most entries error out quickly; that's
   useful here specifically because it stresses `read_bit`'s end-of-input/short-read behavior,
   the part actually changed, far more than the synthetic image does), replayed byte-for-byte the
   same way `fuzz_targets/fuzz_ccitt.rs` interprets them.

A combined hash (synthetic image's `push_pixels`/`next_line` event stream + `Result`, XOR'd with
the corpus replay's same) is printed by every run; a round-trip check (decoded runs == the
encoder's own known input, per row) additionally validates the synthetic image before hashing.

**First measurement attempt (wall-clock, `std::time::Instant`, isolated runs) was actively
misleading** - worth recording since it nearly produced a false "regression" result. Under this
session's host (many sibling perf-optimize candidates building/benching concurrently through the
same shared lock, 24 cores, `uptime` load average 4-10 during this session), single isolated
`taskset -c 2` runs of the patched binary landed consistently ~40-50% slower than the baseline's
own isolated runs (patched p50 ~2.0-2.3ms vs baseline p50 ~1.35-1.4ms, 4 runs each, no overlap
between the two distributions - this looked like a real, reproducible regression, not noise).
Two follow-up checks resolved it:

- **`perf stat -e instructions,cycles`** (deterministic, immune to scheduling/thermal noise) on
  the exact same two binaries, same bench-mode invocation: baseline 4,809,677,468 instructions /
  2,153,684,655 cycles vs patched 4,809,659,853 instructions / 2,149,460,737 cycles - a ~0.0004%
  instruction-count difference and ~0.2% cycle-count difference. Essentially identical.
- **Paired alternating runs** (`baseline,patched,baseline,patched...`, 9 pairs, single-core and
  again unpinned/multi-core - MEASUREMENT.md section 2b's paired-comparison discipline, the
  lesson candidate `035` already recorded for this project): single-core pairs split 4 patched
  faster / 5 baseline faster, multi-core pairs likewise had no consistent winner, all deltas well
  inside run-to-run spread. See raw numbers below.

| Variant | single-core p50 (isolated runs, later shown to be noise) | single-core, `perf stat` instructions | single-core, `perf stat` cycles | paired-run verdict |
|---|---|---|---|---|
| baseline | ~1.35-1.4ms | 4,809,677,468 | 2,153,684,655 | - |
| patched | ~2.0-2.3ms (misleading) | 4,809,659,853 | 2,149,460,737 | 4/9 single-core, no pattern multi-core |

reproduced the same "no difference" result: baseline and patched both p50 ~1.34-1.36ms,
single-core and unpinned.

## Result

**No measurable time change.** The deterministic instruction/cycle counts (`perf stat`) and the
paired alternating-run comparison both agree: this specific bulk-refill implementation does not
measurably speed up `hayro-ccitt`'s CCITT run-length decoding on this synthetic MH-heavy
workload. Only time was measured (no allocation/RSS claim - `BitReader` doesn't allocate either
before or after).

## Why the result looks the way it does

The instruction-count parity is the most informative fact here: the original
`data.get(byte_pos)`-per-bit version, once fully inlined (`decode_run_inner`, `read_bit`, and the
whole call chain down to it are all `#[inline(always)]`), apparently already compiles to
something the branch predictor handles for free (the bounds check is essentially always
in-range and predicts perfectly) - LLVM's codegen for the "cheap, predictable branch on every
iteration" version and this candidate's "amortized bulk load, cheaper apparent per-bit work but
more live state" version end up costing about the same number of instructions per decoded bit.

A plausible reason the added buffering didn't pay for itself: `BitReader` grew from 3
loop-carried scalars (`data` pointer+len, `bit_offset`) to 5 (`+ buffer: u64, buffer_bits: u32`).
Since `decode_run_inner`'s per-bit loop is aggressively inlined together with the state-machine
table lookup (itself needing a live index/pointer and the accumulator), the extra two live values
may be pushing register allocation in that hot region past what it can keep resident without
spilling - this wasn't confirmed by reading disassembly (out of scope for this candidate's
budget) and is offered as a hypothesis, not a demonstrated cause, for why "half as many bounds
checks" didn't translate into "fewer cycles" here.

## Does it change behavior/output?

- **Bit-exact?** Yes. The synthetic-image round-trip and the 207-file corpus replay both produce
  identical hashes (`a85ab73b9e7cee1c` for the synthetic+corpus combined hash) before and after
  the patch, across every build in this session.
- **Is this a breaking change?** No - `BitReader` is `pub(crate)`, not part of `hayro-ccitt`'s
  public API.
- Project test suite, before and after (identical both times, same two failures - both
  pre-existing/environmental, unrelated to this patch, present in a pristine unmodified checkout
  of this worktree too):
  - `cargo test --release -p hayro-ccitt`: 0 tests (crate has none).
  - `cargo test --release -p hayro-syntax`: 199 passed, 2 failed
    (`pdf::tests::pdf_version_catalog`, `pdf::tests::pdf_version_header` - both panic on a
    missing test-asset file via `Result::unwrap()`, i.e. an external file this checkout doesn't
    have, not a logic failure).
  - `cargo test --release -p hayro-tests --test tests -- ccitt --test-threads=4`: 1 passed
    (`render::image_ccitt_rows_below_height`), 1 failed
    (`render::pdfjs_ccitt_EndOfBlock_false` - same missing-external-asset pattern,
    `hayro-tests/pdfs/downloads/pdfjs/ccitt_EndOfBlock_false.pdf` isn't present in this
    checkout).

## What's not done / open questions

- The register-pressure hypothesis above wasn't confirmed via disassembly/`llvm-mca` - if someone
  wants to actually chase a win here, that would be the next step (e.g. a narrower buffer, or
  reusing `bit_offset` itself as the buffer-position tracker instead of a separate
  `buffer_bits` counter, to keep loop-carried state at 4 scalars instead of 5).
- Not tried: refilling only 1-2 bytes at a time (smaller buffer, less state) instead of the full
  8-byte bulk fill - might reduce live state further while still cutting bounds-check frequency
  4-8x; untested.
- The synthetic workload is Group3-1D only (exercises `decode_run_inner` directly, not the
  Group4/2D `decode_mode` path) - `decode_mode`'s own `read_bit` calls (up to 7 bits per mode
  code) weren't separately measured, though they go through the identical `read_bit` this patch
  changes.
