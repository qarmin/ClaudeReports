## How to read it

- **delta** is what candidates 08 (duplicate dependency registrations), 09 and 10
  (gradient paths) are worth on this GPU.
- The **mimalloc** column bounds allocator-side work: it is the same code as *session*
  with a ~3.3x faster allocator, so `session - mimalloc` is roughly what any further
  allocation-removing change (arena, buffer pooling, candidate 06) can still buy.
- Allocation counts are hardware independent; the numbers here should match the ones in
  `FINAL_NUMBERS.md`, which was measured under llvmpipe.

## The artifact in the `scroll` row, and the fix

The session binary reported **617 272** allocations for `scroll 100000` in the main table but
**301 932** for the same scene in the row-variant section of the same run - a factor of 2.04. The
windowed benchmark used whatever size the window manager gave the window, so one run had roughly
twice as many rows visible as the other. That makes the -5.5% delta for that row meaningless: it
compared 1x of work against ~2x of work.

Corrected using the row-variant number, which had the normal window:
**pristine 54.57 ms (703 102 allocations) vs session 49.06 ms (301 932) = -10.1%**, in line with
the -10.8% of the first run.

Fixed in `src/frames.rs`: the windowed benchmark now forces the window to the requested `--size`
(default 1280x860 physical) and prints `window WxH physical, scale factor N` in its report, so any
remaining variance is visible in the output. Verified: the same command on a 1280x900 and a
1600x1200 Xvfb screen now reports identical allocation counts.
