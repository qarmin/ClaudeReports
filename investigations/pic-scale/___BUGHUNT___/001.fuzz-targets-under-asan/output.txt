2. Isolating the cause: is it pic-scale's own resize code, or a generic "ASAN hangs here"
   sandbox issue, or something specific to the libFuzzer/ASAN combination?
=====================================================================

2b. pic-scale's resize_rgba() logic called directly (verbatim copy of the fuzz harness body,
    including the padded stride and double-resample pattern), across a grid of 50,176 cases
    (all combinations of src/dst in {1,2,3,5,7,50,500,2500}x{1,2,3,5,7,50,500}, all 16
    combinations of quality/threading/supersampling/multi_stage flags), NO ASAN, NO libFuzzer:

$ timeout 60 ./target/release/hang_probe > grid.log
exit=0   (ran to completion, all 50176 cases)
$ grep "done in" grid.log | sort -t' ' -k... | head -1   # slowest case
case src=2500x2500 dst=1x1 q=false th=false ss=false ms=true ... done in 10.728804ms
  -> every one of the 50176 cases finished in single-digit milliseconds. No hang, no case
     anywhere close to a second, let alone forever.

2c. Same 50,176-case grid, same resize_rgba() logic, now built directly against ASAN
    (`RUSTFLAGS="-Zsanitizer=address" cargo +nightly build --release --target
    x86_64-unknown-linux-gnu`), bypassing cargo-fuzz/libFuzzer entirely:

$ timeout 60 ./target/x86_64-unknown-linux-gnu/release/hang_probe > asan_grid.log
  -> full 50176-case grid completed within the 60s window (each case ~10-35ms, roughly
     3x slower than without ASAN, as expected from ASAN's allocation overhead - not a hang).
[50176] case src=2500x2500 dst=500x500 q=true th=true ss=true ms=true ... done in 35.335419ms

Conclusion: pic-scale's own resize code is not the source of the hang - it runs to completion,
fast, both with and without ASAN, across the same extreme parameter space the fuzz harness
explores. The hang is specific to the combination of {cargo-fuzz's libFuzzer driver} +
{AddressSanitizer} in this sandboxed environment - most likely something in libFuzzer's own
ASAN-instrumented execution/RSS-watchdog loop interacting badly with this container (LeakSanitizer
was ruled out as the sole cause, since ASAN_OPTIONS=detect_leaks=0 only prevented the hang on
1 of 11 trials, not reliably).
