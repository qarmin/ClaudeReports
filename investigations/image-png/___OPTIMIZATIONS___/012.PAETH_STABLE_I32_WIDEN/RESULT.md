# Paeth unfiltering on stable x86_64: widen `filter_paeth_stbi`'s intermediate type from i16 to i32

`rustc 1.98.0 (88d9e12ae 2026-08-18)`, `cargo 1.98.0`, also cross-checked on `nightly-x86_64-unknown-linux-gnu` (dated build matching the same day) for the `unstable`-feature fact below. x86_64, 24 logical cores, default `cargo build --release` (no `-C target-cpu=` tuning, matching how the crate ships).

Issue #511 ("Vectorize Paeth filtering on stable") is the cited source for this candidate. Two things worth stating up front, both established by reading the *full* issue thread (not just the opening post, which only shows the early exploration) and by direct experiment on this machine:

1. **The premise "Paeth is the one filter that needed nightly std::simd" no longer holds for x86_64 on the current `HEAD` (05ccdb9).** `src/filter/paeth.rs` has a separate `#[cfg(target_arch = "x86_64")]` `unfilter()` that unconditionally uses the autovectorized `filter_paeth_stbi` scalar formulation for every `BytesPerPixel` variant (1/2/3/4/6/8) - this is exactly the "stable formulation that autovectorizes" the issue asked for, and it was already merged via PRs #512/#513/#539 (confirmed via `git log --oneline --all | grep paeth`). The nightly `unstable` feature's `src/filter/simd.rs` Paeth kernels (`paeth_unfilter_3bpp`/`paeth_unfilter_4bpp`) are only wired into the *other* `#[cfg(not(target_arch = "x86_64"))]` `unfilter()` (i.e. ARM/other targets) - confirmed empirically: `cargo +nightly build --release --features unstable` on this x86_64 machine emits `warning: function 'paeth_unfilter_3bpp'/'paeth_unfilter_4bpp'/'process_paeth_chunk_bpp4_s64' is never used` for all of them. So on x86_64, `--features unstable` has **zero effect** on Paeth unfiltering today; there was nothing nightly-only left to "vectorize on stable" here.
2. Given that, the only genuinely open, testable idea left in the issue thread for x86_64 is Shnatsel's own late suggestion (2024-09-28/29 comments): widen the arithmetic in `filter_paeth_stbi` from `i16` to `i32`, which he reported "vectorizes fine on modern CPUs... but fails on base x86-64 and performance plummets" - this candidate actually runs that experiment on real hardware rather than citing the comment secondhand.

## What was tried

Patch: change `filter_paeth_stbi(a: i16, b: i16, c: i16) -> u8` to `(a: i32, b: i32, c: i32) -> u8`, and widen the `a_bpp`/`c_bpp` state arrays and `as i16` casts to `i32` throughout the x86_64 `unfilter()` (all 6 `BytesPerPixel` arms use the same helper, so this is one cohesive change - see `patch.diff`, `+44/-44` in `src/filter/paeth.rs` only). No `-C target-cpu` flags were added; default codegen only, matching what the crate ships to users.

Harness: `benches/unfilter.rs --features benchmarks` (criterion), filtered to `filter=Paeth`, all 6 `bpp` values it already covers, random-byte rows (the harness's own input, not real image data - noted as a caveat below). **This bench currently fails to build against the `rand` version that a fresh `cargo` resolves today** (`rand = "0.10"` in `Cargo.toml` resolves to `rand 0.10.2`, whose top-level re-export list dropped `TryRngCore` - see "Incidental finding" below); a one-line harness-only fix (`use rand::TryRngCore;` -> `use rand::TryRng;` in `benches/unfilter.rs`) was applied locally to get it building, is **not** part of `patch.diff` (it touches the harness, not the library), and was reverted along with everything else at the end.

Single-core: `taskset -c 3`, 2 independent runs per configuration (baseline x2, patched x2) to establish the noise floor per MEASUREMENT.md. Multi-core: same bench unpinned (no `taskset`), 1 baseline + 2 patched runs (criterion's own internal repeat/warmup already gives per-run statistics; the runs were repeated across separate process invocations, not just criterion's own resamples).

## Result

**Mixed - real, reproducible wins on bpp=2/3, a real, reproducible, severe regression on bpp=4 and a smaller one on bpp=6, no measurable change on bpp=1/8.** Time only (no allocation/RSS dimension - this patch doesn't touch allocation behavior). The bpp=4 case is the one that matters most in practice: it's RGBA, the exact color type profiled in issue #567 (43-56% of decode time on a real photo), and it's a +50-64% regression, not a rounding error - taking this patch as-is would make the single most commonly profiled real-world case substantially slower.

## Does it change behavior/output?

- **Bit-exact?** Yes. The project's own exhaustive equivalence test (`filter::paeth::tests::paeth_impls_are_equivalent`, `#[ignore]`d by default because it iterates all 256^3 `(a,b,c)` combinations) was run explicitly with `cargo test --release paeth_impls_are_equivalent -- --ignored` on the patched tree and passed. Widening `i16` to `i32` cannot change the result: `thresh = c*3 - (a+b)` stays within roughly [-765, 765] either way, far inside both types' range, so there is no overflow/wraparound difference between the two.
- **Is this a breaking change?** No - `filter_paeth_stbi` is `pub(super)`, not part of the public API, and no output changes.
- Project test suite (`cargo test --release`): **107 passed, 0 failed, 1 ignored, both before and after** (91 lib unit tests + 1 + 4 + 3 + 8 doc-tests across the 4 test binaries + doc-tests, identical counts in both runs). No new failures.

## Why the result looks the way it does

This reproduces, on real hardware with no special flags, exactly what Shnatsel already found and reported in issue #511 on 2024-09-29: widening to `i32` makes LLVM's autovectorization decision flip in a bpp-dependent way - better for bpp=2/3 (probably because the wider lane width lets more pixels' worth of state fit a vector register profitably at that stride), worse for bpp=4/6 (likely the reverse: the wider type now needs more vector registers/spills for the same pixel-batch, or crosses a shuffle/gather threshold LLVM's cost model penalizes on plain `x86-64` without `-C target-cpu=x86-64-v3`). This candidate didn't disassemble the generated code to pin down the exact codegen difference (issue #511's own godbolt links from the same investigation are the closest existing evidence for that, and are consistent with this result), since the measured outcome alone is already decisive enough to answer the "is this worth taking" question mixed-and-negative on the case that matters most.

## What's not done / open questions

- Not tried: `-C target-cpu=x86-64-v3` (Shnatsel's own comment says both the i16 and i32 versions "benefit... but the difference isn't dramatic", and the crate doesn't ship with a target-cpu override today, so measuring under a flag the crate doesn't actually use didn't seem like the more useful use of time here).
- Not tried: a per-bpp split (keep `i16` for bpp=4/6, use `i32` only for bpp=2/3) - technically possible (two differently-typed private helper functions, or a `const BPP` generic parameterized on width) but adds real complexity to `paeth.rs` for a combined win that's smaller than the current file's existing per-arch/per-bpp branching already is; flagged here as an idea rather than implemented, since a partial win on 2 of 6 bpp values, at the cost of doubling the helper-function surface, needs a maintainer call on whether it's worth the added branching, not a default "yes."
- Not disassembled: no objdump/godbolt-level confirmation of *why* bpp=4/6 regress under `i32` on this machine - see "Why the result looks the way it does".
- **Incidental finding, not folded into `___BUGHUNT___/` (not a library bug - see below):** `benches/unfilter.rs` currently fails to build with a fresh, unpinned `cargo` (`Cargo.lock` isn't committed for this crate) because `rand = "0.10"` in `Cargo.toml` resolves to `rand 0.10.2`, and none of the published `rand 0.10.x` versions (checked 0.10.0/0.10.1/0.10.2 registry sources directly) re-export `TryRngCore` from their crate root - only `TryRng`/`TryCryptoRng`/`CryptoRng`/`Rng`/`SeedableRng` are re-exported; `TryRngCore` only exists in `rand_core` itself (`rand::rand_core::TryRngCore`). The fix is a one-line harness change (`use rand::TryRngCore;` -> `use rand::TryRng;`, which has the same `try_fill_bytes` method) - not included in `patch.diff` since it's a harness file, not the library being optimized. Every session reaching for `benches/unfilter.rs`, `benches/adam7.rs`, or `benches/expand_paletted.rs` (all `--features benchmarks`, all likely sharing similar helper code) should expect to need this same fix until either `Cargo.toml`/the bench file is updated upstream or a `Cargo.lock` is committed to pin an older `rand`.
