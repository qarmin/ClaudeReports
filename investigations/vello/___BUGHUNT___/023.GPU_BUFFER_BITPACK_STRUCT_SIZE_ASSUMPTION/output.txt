Note the aliasing in the pristine tree: width=65536 and width=131072 both decode back to a
completely different, mutually-indistinguishable width (0) despite representing very different
declared image sizes - this is unbounded modular wraparound, not a bounded/predictable clamp.

Also note: the "end-to-end resolve()" line is 0x00000000 for EVERY case with width or height >
8192 in this run, INCLUDING width=65535 (which is *not* corrupted by the 16-bit packing bug at
all - it round-trips correctly as shown by "decoded=(65535, 1) OK" on the line above it). This is
because `vello_encoding::image_cache::MAX_ATLAS_SIZE` is a hardcoded 8192, independent of this
bug: `Resolver::resolve` explicitly zeroes both the atlas xy and width_height words whenever an
image fails to fit the atlas, for ANY oversized image, corrupted or not. Since 65536 (this bug's
trigger threshold) is always > 8192 (the atlas's own unrelated cap), every input that triggers
this packing bug is ALSO independently zeroed by that pre-existing safety net before reaching the
real GPU-submitted buffer through vello::Renderer's actual pipeline. See RESULT.md for the full
discussion of what this does and doesn't mean for "Confirmed".

Note: `check()`'s simple exact round-trip test necessarily still reports "CORRUPTED"/"REPRODUCED"
in the release build after the fix, because a dimension >= 65536 fundamentally cannot be encoded
losslessly in a 16-bit field - clamping, not exact preservation, is the only sane release-mode
option once debug_assert is compiled out. The actual improvement in the release build is visible
in the *values themselves*: every out-of-range case now clamps deterministically to the same
bounded maximum (65535), instead of wrapping unpredictably to values that alias with completely
different, legitimately-sized images (e.g. width=65536 no longer decodes identically to
width=131072 - compare the BEFORE block above, where both decode to width=0).
