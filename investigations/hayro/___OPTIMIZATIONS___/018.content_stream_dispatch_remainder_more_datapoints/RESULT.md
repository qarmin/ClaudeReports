# Third/fourth/fifth data points for candidate 007's `Tf`-resolution-cache fix

Backlog entry from `../IDEAS.md`: candidate 007 measured a -16% to -18% `render()` win from
caching the resolved `Tf` (text font selection) font by resource name, on `img.pdf` (326 `Tf`
calls/page). Candidate 012 re-ran the identical patch against `fonts_type1_latex.pdf` (26 `Tf`
calls/page) and found no measurable change. This candidate adds three more data points using the
same, byte-for-byte identical `patch.diff`: `issue391.pdf` and `image_cmyk_icc_jpg.pdf` (both
named explicitly in the backlog entry, already present in `hayro-tests`' corpus) plus a synthetic
`cache_defeating.pdf` built for this candidate to test the backlog's other still-open question -
"no PDF with an actively cache-defeating pattern (a different font on every single `Tf` call) has
been tried either."

## What was tried

No new source code was written for the actual fix; only the bench's input selection changed (a
`--pdf <name>` argument selecting between three embedded PDFs). `patch.diff` in this folder is
byte-for-byte identical to candidates 007 and 012's.

### The three inputs

- **`issue391.pdf`** (`hayro-tests/pdfs/load/issue391.pdf`, real corpus file): first page has
  **34** `Tf` operator calls (counted directly via a temporary `AtomicU64` counter added to
  `hayro-interpret::interpret()`'s `TextFont` arm, run once per PDF, then reverted before any
  benchmarking - not a byte-search, since this PDF uses `FlateDecode`-compressed content streams
  unlike `fonts_type1_latex.pdf`). A third real-world, text-bearing data point, close to candidate
  012's 26.
- **`image_cmyk_icc_jpg.pdf`** (`hayro-tests/pdfs/custom/image_cmyk_icc_jpg.pdf`, real corpus
  file): first page has **0** `Tf` calls (confirmed the same way) - it is a single full-page CMYK
  JPEG image with no text at all. Included as a "does the fix cost anything when its code path is
  never exercised" check, not a frequency-scaling data point (there is no `Tf`-call frequency to
  scale from).
- **`cache_defeating.pdf`** (synthetic, generated by `testdata/gen_cache_defeating_pdf.py`, kept
  in this folder for reproducibility): a minimal, hand-built single-page PDF (no compression, no
  embedded font programs - all fonts are standard-14 names) with **326** `Tf` calls (matching
  `img.pdf`'s count exactly for a fair magnitude comparison) that round-robin through 8 distinct
  standard fonts (`Helvetica`, `Helvetica-Bold`, `Times-Roman`, `Courier`, `Helvetica-Oblique`,
  `Times-Bold`, `Times-Italic`, `Courier-Bold`), so **no two consecutive `Tf` calls ever reference
  the same font** - the worst case for a resource-name-keyed cache, which therefore misses on
  every single call.

Bench: `bench/src/main.rs`, extending the candidate 007/012 bench pattern (path-dependency on
`hayro`, 300 iterations, 10% warmup discarded, min/p50/mean/p95/max of `render()` wall time, FNV-1a
hash of the produced pixmap's premultiplied RGBA8 bytes checked every iteration for bit-exactness)
with a `<pdf-name>` CLI argument selecting which of the three embedded PDFs to render.

### Measurement

Measured against the real hayro working tree at commit `5a5f0e24` (this candidate's
`base_commit`), `taskset -c 2` (single-core) and unpinned (multi-core/realistic), each run twice
per variant. The host's `uptime` load average was fluctuating during this session (unrelated host
activity outside this sandbox - `uptime`'s load average reflects the host, not this container);
an initial pass taken while load was elevated (~13-14, mean/p95/max inflated ~2x uniformly across
*all three* PDFs including `image_cmyk_icc_jpg.pdf`, which has zero relevant code path to regress)
was discarded as a clear noise confound and every number below was re-measured once load had
settled back to ~5-7 (`uptime` shown before each block; p50s stayed consistent within ~2% across
repeats at that point, `min` values were essentially flat throughout even during the noisy pass -
supporting evidence that the earlier spike was scheduler contention, not the code path).

## Result

**No measurable change for any of the three inputs**, in either direction:

- **`issue391.pdf`** (34 `Tf` calls/page): baseline p50 clusters at 18.06-18.54ms, patched at
  18.15-18.46ms - within this bench's own run-to-run spread (~1-2%). Consistent with candidate
  012's `fonts_type1_latex.pdf` finding (26 `Tf` calls, also no measurable change) - both real
  PDFs at this end of the frequency range see a saving too small to resolve.
- **`image_cmyk_icc_jpg.pdf`** (0 `Tf` calls/page): baseline and patched are statistically
  identical (2.65-2.72ms both ways) - expected, since a page with no `Tf` operators never reaches
  the patched code path at all. This confirms the fix has no measurable fixed cost even when its
  cache is never populated or consulted.
- **`cache_defeating.pdf`** (326 `Tf` calls/page, always a cache miss): baseline p50 3.14-3.17ms,
  patched p50 3.18-3.26ms - a ~1-3% difference that overlaps the noise band observed elsewhere in
  this same measurement session (compare `issue391.pdf`'s own 18.06-18.54ms baseline spread) and
  is not clearly distinguishable from run-to-run variance. If real, it would represent the
  small, expected constant overhead of one extra `FxHashMap` lookup-then-insert per `Tf` call
  (`resolved_font_cache`) on top of the pre-existing `font_dict_cache` path, in the specific case
  where that extra cache never pays for itself - but it is not large enough here to call a
  reproducible regression versus this bench's own noise floor.

## Does it change behavior/output?

- **Bit-exact?** Yes, for all three PDFs. Every iteration of every run (baseline and patched)
  produced the identical pixmap hash for that PDF.
- Project test suite: ran `cargo test --release -p hayro-tests --test tests -- render` before and
  after the patch (same command candidates 007/012 used). Both runs: 267 passed, 1259 failed, 181
  filtered out. Diffed the two runs' failing-test-name sets (extracted via `render::[A-Za-z0-9_]+`
  to strip the non-deterministic thread-id noise in the raw panic output): **identical set**
  (1525/1525 unique failing test names match). As in 007/012, every failure is a missing local
  test-asset file (`Os { code: 2, kind: NotFound }`), the same pre-existing environmental
  limitation of this sandbox, not a render regression.
- **Is this a breaking change?** No - same patch as candidates 007/012, internal to
  `hayro-interpret::interpret()`, no public API change.

## Why the result looks the way it does

This adds three data points that together bound the fix's behavior at both ends of the
`Tf`-frequency spectrum without finding an actively harmful case:

1. `issue391.pdf` (34 calls) sits in the same "too infrequent to resolve above noise" regime as
   candidate 012's `fonts_type1_latex.pdf` (26 calls) - both far below `img.pdf`'s 326, where the
   win was clearly visible. The frequency threshold where the win starts being resolvable above
   this bench's ~1-2% noise floor is still not pinned down exactly, only bracketed: somewhere
   above 34 calls/page and at or below 326.
2. `image_cmyk_icc_jpg.pdf` (0 calls) is not on that spectrum at all - it's a control showing the
   fix adds no overhead to pages that never call `Tf`.
3. `cache_defeating.pdf` (326 calls, guaranteed-miss pattern) shows the fix does **not** turn into
   a measurable regression even in its worst case: the extra `resolved_font_cache` lookup-then-
   insert per call is cheap enough (a short `Name` hash/compare, not the SipHash-over-raw-bytes
   the original path always paid) that missing it every single time still doesn't show up above
   noise here, on this same page shape (326 calls) where the *hit* case saved 16-18%.

Together, this suggests the fix's downside risk (a PDF that pathologically switches fonts on every
`Tf` call) is small-to-none, while its upside is real but concentrated in the specific case
`img.pdf` represents: many `Tf` calls reusing a small set of fonts.

## What's not done / open questions

- The exact `Tf`-frequency threshold where the win crosses this bench's noise floor is still not
  located - only bracketed between `fonts_type1_latex.pdf`/`issue391.pdf`'s 26-34 (no change) and
  `img.pdf`'s 326 (strong win). A page with, say, 100-150 `Tf` calls reusing few fonts would be a
  useful next data point if this matters to someone deciding whether to take the patch.
- `cache_defeating.pdf`'s small, inconclusive (noise-comparable) increase was not investigated
  further (e.g. with `perf`, unavailable in this sandbox, or callgrind) - it's reported as
  "not distinguishable from noise" rather than confirmed zero, since a bounded, real few-percent
  constant-factor cost is plausible given the code (one extra hashmap round-trip per call) even
  if it wasn't resolvable here.
- `cache_defeating.pdf` uses only 8 distinct standard fonts in strict round-robin, not fully random
  reuse patterns or a much larger number of distinct fonts (e.g. hundreds of embedded fonts on one
  page) - an even more extreme cache-defeating shape was not tried.
- The host-level load-average noise encountered mid-session (see "Measurement" above) is worth
  keeping in mind for any future session on this same machine: `uptime`'s load average reflects
  the host, not this container, so a spike can appear and disappear independent of anything this
  session is doing, and it inflated mean/p95/max uniformly across unrelated PDFs when it happened
  - a useful confound signature to recognize quickly next time (real regressions from a code
  change don't uniformly hit an unrelated 0-`Tf`-call control PDF).
