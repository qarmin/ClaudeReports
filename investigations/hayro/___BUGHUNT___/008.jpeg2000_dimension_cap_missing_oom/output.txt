=== Separate observation: same PoC PDF via the top-level `hayro::render` entry point ===

Driving the identical PoC PDF through the full `hayro` crate's own top-level `render()` (which
passes a CTM-derived `target_dimension` hint into `RasterImage::with_rgba`, unlike the
`interpret_page`/`Device`-with-`None` path used by `repro/`) does NOT abort the same way within
30 seconds - it appears to hang/thrash instead (killed by `timeout 30`, exit 124/143, no crash
message). This was not chased further (see RESULT.md "What's not done"): the hint computation in
`hayro/src/image.rs::draw_pdf_image` (`target_width = (transform * Point::new(image.width() as
f64, 0.0)).to_vec2().length()`) multiplies the placement matrix's scale by the image's *raw
pixel width* rather than dividing by it, so for this PoC's `cm 100 0 0 100 50 50` placement the
resulting `target_width` (~100 * 100000 = 10,000,000) ends up far larger than the native
100000px width regardless of how small the image is actually drawn on the page - meaning the
resolution-skip optimization essentially never downscales in this code path, and the full
100000x100000 decode is requested here too. It manifests as a slow-not-abort in this particular
run rather than a clean allocator failure; this is noted as a related but distinct observation
and was not root-caused as its own candidate this session.
