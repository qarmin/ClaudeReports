# Extend rayon threshold+guard to remaining LUT/numeric-conversion dispatch sites

`pixeldata/src/lib.rs` has several more unconditional `#[cfg(feature = "rayon")]` dispatch points
beyond `convert_colorspace_u8`/`u16` (candidate 003): the 8-bit and 16-bit monochrome-image LUT
sites (feeding `mono_image_with_extend_par`/`mono_image_with_narrow_par`) and `convert_pixel_slice`'s
5 LUT/plain-numeric-conversion `to_vec`-style sites (8-bit LUT, 8-bit plain, 16-bit LUT, 16-bit
unsigned plain, 16-bit signed plain). Carried over as a well-specified lead from a prior session's
notes (candidate 010 in `~/.claude/skills/perf-optimize/projects/dicom-rs.md`), re-implemented and
re-measured fresh here (base commit `df2b9e4236298efa3fa37a1f360fc4bf284d586a`) - **this
re-verification found a different, and overall less favorable, result than the prior notes
described** (see Result below).

## What was tried

Added the same `rayon_worth_it()`/`LUT_RAYON_PIXEL_THRESHOLD` (16,384, reusing candidate 003's
value since these sites do comparably cheap per-element work) guard to all 7 unconditional rayon
dispatch points found in this file for LUT-mapped and plain-numeric pixel conversion: 2
`mono_image_with_extend_par`/`_narrow_par` call sites, and 5 `convert_pixel_slice` call sites
(8-bit LUT, 8-bit plain grayscale, 16-bit LUT, 16-bit unsigned plain, 16-bit signed plain). Each
site's existing `#[cfg(feature = "rayon")]` block was restructured from an unconditional
parallel-only path into an `if rayon_worth_it() && <slice>.len() >= LUT_RAYON_PIXEL_THRESHOLD { par
} else { sequential }`, with the `#[cfg(not(feature = "rayon"))]` branch (sequential-only,
unaffected) left as-is.

Bench: `___OPTIMIZATIONS___/harness/bench_pipeline`'s new `tovec` mode
(`decode_pixel_data().to_vec_frame::<f32>(0)`, isolating `convert_pixel_slice`) and the existing
`colorspace`/`dump-image` modes (which also exercise `mono_image_with_extend_par`/`_narrow_par`
via `to_dynamic_image` for a monochrome image), against two new synthetic MONOCHROME2 fixtures
generated by a new `gen-mono` mode: `mono_below.dcm` (real `pydicom/MR_small.dcm`, 64x64=4,096px,
16-bit, below the 16,384px threshold - hits the 16-bit LUT site) and `mono_above.dcm` (real
`pydicom/vlut_04.dcm` tiled 4x via `gen-mono`, 2048x512=1,048,576px, 8-bit, above threshold).

| Variant | below-threshold (4,096px, 16-bit LUT site) | above-threshold (1,048,576px) | single-core (no-rayon build, below-threshold) |
|---|---|---|---|
| baseline (unconditional rayon) | 0.435/0.438 ms (2 rounds) | 0.348/0.231 ms (2 rounds) | 0.080 ms |
| patched (threshold+guard) | 0.493/0.502 ms (2 rounds, REGRESSION) | 0.334/0.236 ms (2 rounds, no change) | 0.080 ms (no change) |

## Result

**Below the threshold: a real, reproducible +13.2%/+14.5% REGRESSION on the 16-bit LUT site (2
rounds, `RUNS=9` and `RUNS=15`, both fully consistent - 0/9 and 1/15 patched wins), the opposite of
the intended effect.** This is unexpected given the guard, when it takes the sequential branch, is
supposed to run the exact same code as baseline. **Above the threshold: no consistent change** (2
rounds, 5/9 and 4/9 - not consistent), as expected since both builds take the same parallel path
there. **Single-core (`--no-default-features --features image,native` build, no rayon linked):
no consistent change** (+0.0%, 2/9 - not consistent) - critically, this confirms the regression is
specific to the rayon-*enabled* build reaching the sequential branch through a runtime `if`, not a
fundamental slowdown of the sequential code itself (which is textually identical in both builds
when compiled without the `rayon` feature).

**This is a different, and more clearly negative, finding than the prior session's notes**, which
reported "5/6 sites clean wins" with only the 16-bit `mono_image_with_narrow_par` site showing an
unexplained regression *above* ~300K-1.3M px. This session's regression is on a different site
(the 16-bit LUT branch inside `convert_pixel_slice`, not `mono_image_with_narrow_par`) and in the
opposite size range (*below* the threshold, where no code-path change should even be observable).

## Does it change behavior/output?

- **Bit-exact?** Yes, in every configuration tested (below/above threshold, both `tovec` and
  `dump-image` checksums/hashes match between baseline and patched builds). Only the dispatch
  mechanism changed, never the arithmetic.
- **Is this a breaking change?** No public API/type changes. `LUT_RAYON_PIXEL_THRESHOLD` and
  `rayon_worth_it()` are private; `rayon_worth_it()` here is a separate, textually-identical
  duplicate of the one in candidates 003/004 (each candidate's patch is self-contained and
  independently applicable, so this is intentional duplication, not a bug - see MEASUREMENT.md's
  "one fix per candidate" discipline).
- Project test suite: **537 passed / 0 failed / 6 ignored, both before and after** (full
  `cargo test --workspace`, including doctests) - no new failures.

## Why the result looks the way it does

Not confirmed with a disassembler/profiler this session (bounded time, per SKILL.md's guidance on
regressions) - the leading, unconfirmed hypothesis is that wrapping the previously
`#[cfg]`-selected (compile-time-only) branch choice in a runtime `if` prevents the compiler from
proving statically which branch executes, which can defeat monomorphization-driven inlining or
other optimizations LLVM was previously able to apply to `lut.map_iter(...)`/`.collect()` when it
was the *only* reachable code in that build. This is consistent with the single-core (no-rayon)
build showing zero effect: there, the `if`/`else` doesn't exist in the first place (the whole block
is `#[cfg(feature = "rayon")]`), so there's nothing to defeat. This differs from candidates 003/004,
where the same kind of runtime guard did NOT show a below-threshold regression - a plausible reason
is that `convert_colorspace_u8`/`interleave`'s per-element bodies are small, self-contained
closures/functions with no generic `Lut<T>`/`NumCast` machinery, so there was less for the compiler
to lose by not proving branch-exclusivity statically; `convert_pixel_slice`'s LUT path is
considerably more generic (`Lut<T>`, `T: NumCast + Send + Sync`), which may be more sensitive to
this effect. This is a plausible mechanism, not a confirmed one.

## What's not done / open questions

- Root cause not confirmed - no disassembly/objdump comparison was done this session (unlike
  candidate 007's approach in the prior notes) to verify the inlining-defeat hypothesis above.
  A future session with more budget could confirm this with `objdump -d -C` on both builds' hot
  symbols, the same technique described in this workspace's own prior notes for a similar question.
- Only the 16-bit LUT site (`convert_pixel_slice`, `samples.into_par_iter()`/`into_iter()`) was
  directly measured below threshold. The other 4 sites sharing the same guard pattern (8-bit LUT,
  8-bit plain, 16-bit unsigned/signed plain) were bit-exactness-checked (via the same fixtures'
  `dump-image`/`tovec` output matching) but not separately timed below threshold - given the
  regression found on one site, it would be worth checking each of the other 4 individually before
  drawing any conclusion about them specifically; this session ran out of allotted candidate time
  budget before doing so.
- Whether reworking the guard to preserve static branch-exclusivity (e.g. two separate
  monomorphized helper functions selected via a match on a bool computed once outside any hot
  per-element loop, rather than an inline `if`/`else` around the whole collect expression) would
  recover the win without the regression was not attempted - a plausible follow-up, left in
  `IDEAS.md`.

## Follow-up (2026-08-25): partial confirmation via symbol size

Spent a bounded ~15 minutes checking the inlining-defeat hypothesis above via `nm -C -S` on the
harness binary (`to_vec_frame::<f32>`, the function containing the regressed 16-bit LUT site):
**baseline 0xbcc = 3,020 bytes, patched 0xded = 3,565 bytes - an 18% code size increase for the
same logical function.** This is consistent with (but does not conclusively prove) the
inlining/monomorphization-defeat hypothesis: generating separate code for both branches of the new
runtime `if`, without the compiler being able to prove one side dead the way `#[cfg]` guaranteed,
plausibly prevents some sharing/optimization the compiler previously had contributing to a leaner,
faster function body. A full `objdump -d -C` comparison to pinpoint exactly which instructions
differ in the actually-executed sequential path was not attempted (out of this follow-up's own
bounded time) - this is suggestive corroborating evidence, not a confirmed root cause.

## Reproducibility check (2026-08-26): harness no-rayon-build bug fix

Candidate 023's session found and fixed a real bug in `harness/bench_pipeline/Cargo.toml`: the
"`--no-default-features --features image,native` build, no rayon linked" methodology this
candidate's own single-core measurement (above) describes could not, as the harness `Cargo.toml`
existed at the time, actually strip `rayon` (`dicom-pixeldata`'s dependency line had no
`default-features = false`, so its own default `rayon` feature stayed linked regardless of flags
passed to the harness build - confirmed via `nm target/release/bench | grep -c rayon_core` = 386,
not 0, before the fix). This raised a real question flagged in `projects/dicom-rs.md`: was this
candidate's own "single-core: no consistent change" conclusion actually measuring a rayon-free
build, or was rayon silently still linked and the guard's `if size >= threshold` branch still
reachable?

Re-ran this candidate's exact single-core check (`tovec mono_below.dcm 3000`, `taskset -c 0`) using
the harness's *now-fixed* `--no-default-features` build, confirmed genuinely rayon-free via `nm |
grep -c rayon_core` = 0 for both baseline and patched binaries this time. **Result: still no
consistent change (-0.0%, 3/9 paired wins for the patch)** - identical conclusion to the original
measurement. Also re-confirmed, with fresh default (rayon-enabled) builds, that the below-threshold
regression (+13.5%, 0/9, this session) and the above-threshold no-change (+2.3%, 4/9, not
consistent, this session) both still reproduce as originally reported.

**Conclusion: this candidate's original findings all hold up under the corrected harness build -
the harness bug did not affect this candidate's own reported numbers.** (The bug was a latent risk
for any past single-core rayon-guard measurement in this workspace, not a confirmed problem for all
of them - this is the first one actually re-checked; candidates 002/003/004/009/012/018's own
single-core numbers remain unverified against the fix, per the open note in `projects/dicom-rs.md`.)

## Individual per-site re-measurement (2026-08-26), partial - `IDEAS.md`'s open item

The original session only directly timed the 16-bit LUT site below threshold (the one that
regressed); the other 4 guarded sites (8-bit LUT, 8-bit plain, 16-bit unsigned plain, 16-bit
signed plain) were only bit-exactness-checked, not timed. Attempted a fuller pass this session,
bounded by fixture availability:

- **8-bit plain** (`convert_pixel_slice`'s `_ =>` arm, non-monochrome/no-LUT path), below
  threshold: `ybr_below_threshold.dcm` (a small YBR/RGB fixture, correctly reaches this arm since
  it's non-monochrome) - **7/9 paired wins for the patch, -8.6%, does NOT clear this workspace's
  consistency bar (needs >=8/9 or <=1/9)**. Unlike the 16-bit LUT site's clean, fully consistent
  0/9 regression, this site shows no confirmed effect either way - genuinely noisy at this small
  fixture's scale, not a second regression.
- **8-bit LUT** (monochrome + Default modality LUT path), only an above-threshold fixture was
  available (`vlut_04.dcm`, 512x512=262,144px, monochrome, 8-bit) - not useful for a below-threshold
  check (the specific size regime where the 16-bit LUT site regressed); not measured below
  threshold for lack of a suitable small monochrome 8-bit fixture in this workspace's `testdata/`.
- **16-bit unsigned plain / 16-bit signed plain**: not reached - `tovec`'s default
  `ConvertOptions` sends every monochrome fixture through the LUT arm (`ModalityLutOption::Default`),
  and no non-monochrome 16-bit fixture with `PlanarConfiguration::Standard` was available in
  `testdata/` (the `planar_*.dcm` fixtures present all have `PlanarConfiguration=1`, which
  `convert_pixel_slice` rejects outright before reaching either plain arm). Would need either a
  harness mode that forces `ModalityLutOption::None` on a monochrome 16-bit fixture, or a new
  synthetic non-monochrome 16-bit fixture with standard planar configuration - neither built this
  session.

**Net for this pass: no second regression found (8-bit plain is inconclusive, not confirmed bad),
but 16-bit unsigned/signed plain and below-threshold 8-bit LUT remain genuinely unmeasured** - this
item is not fully closed, still worth a real fixture-building effort in a future session if pursued
further (see `IDEAS.md`).

## Related finding from an independent re-derivation: `mono_image_with_narrow_par` regression

A separate re-derivation of this same candidate applied only `rayon_worth_it()` (no pixel-count
threshold) to the same call sites plus the two `build_monochrome_image` sites (`mono_image_with_extend_par`/
`mono_image_with_narrow_par`), not covered by this file's own measurements above. 5 of 6 sites
measured as clean single-core wins (-4.6% to -16.2%), but the 16-bit `mono_image_with_narrow_par`
call site (`to_dynamic_image` on a 16-bit monochrome source) showed a real, size-dependent
*regression* on single-core once past ~300K-1.3M px (+14.4% to +24.5%, decisive at RUNS=15) despite
being a win below that (-7.1%/-7.2% at 262,144px) - not root-caused, but suspected to be a codegen
difference specific to that site's `Vec<u16>`-via-`ImageBuffer::from_raw` consumption path rather
than the runtime-`if` inlining-defeat hypothesis above (see "Why" in that session's notes). This is
a different call site than this file's own regression (`convert_pixel_slice`'s 16-bit LUT branch)
but reinforces the same overall conclusion: **this file's rayon dispatch sites do not uniformly
benefit from a guard/threshold - each site needs independent verification, not just extension of
the pattern from `convert_colorspace_u8`/`interleave()`.**
