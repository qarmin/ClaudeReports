NOTE
=====================================================================
In both runs, the outer "Could not read data set token" (object/src/lib.rs's ReadToken,
Display-only) is unchanged - that's dicom-object's generic wrapper around any DataSetReader
error, exactly matching the original issue's reported message. What changes is the *underlying
source error* (visible via {:?} / Error::source()): before the patch it's an opaque
`ReadValue { ... UnexpectedEof ... }` with no indication of what went wrong; after the patch it's
a new, specific `ElementLengthExceedsContainer` error naming the offending tag, its bogus
declared length, and how many bytes actually remained in its enclosing item.

None of the triggering variations parse successfully after the patch - the fix does not achieve
dcmtk-level interoperability with these files (that would require heuristically distinguishing
"opaque binary payload" from "real nested data set" inside a CP-246 item, which real-world DICOM
toolkits like dcmtk/GDCM implement as a nontrivial guessing routine - judged out of scope for a
bounded fix here). See RESULT.md.
