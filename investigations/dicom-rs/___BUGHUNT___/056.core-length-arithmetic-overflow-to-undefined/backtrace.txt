This confirms the bug has two distinct manifestations depending on build profile: an uncatchable
panic in debug/test builds (via the pre-existing `debug_assert!`), and silent, undetected
corruption to `Length::UNDEFINED` in release builds (the `debug_assert!` compiles out entirely,
letting the wrapped `u32` arithmetic's result flow through unchecked).

=== Provenance ===

Found via git archaeology: `git log --all --grep="#768"` surfaced an unmerged remote branch
(`origin/fix/length-arithmetic-overflow`, commit `dd6e81aa`, authored "Co-Authored-By: Claude
Sonnet 4.6") titled "fix(core): prevent Length arithmetic from silently wrapping to UNDEFINED
sentinel", referencing external report items OVF_3/OVF_4/OVF_5. `git merge-base --is-ancestor
dd6e81aa df2b9e42` confirmed this commit is **not** part of the current tree's history - the fix
was never merged into master, so the bug it describes is still live in the exact commit
(`df2b9e42`) this bug-hunt session is auditing.

That unmerged fix was independently verified by reproducing the described defect from scratch
(the two example call sites above, `Add<Length>` and `SubAssign<i32>`), and found to be
**incomplete**: it only touched `Add<Length>`, `SubAssign<i32>`, and `DataElement::update_value`,
leaving `Add<i32>` and `SubAssign<Length>` with the exact same unguarded `debug_assert!`-only
pattern. This candidate's fix covers all five call sites (the three already described externally,
plus the two the external fix missed), verified against fresh, hand-built reproductions for all
four arithmetic operators. `update_value`'s analogous fix (capping `byte_len` before the `u32`
cast) was carried over by direct analogy - it shares the exact same root cause but requires
allocating close to 4 GiB to trigger in practice, so it was not independently reproduced with its
own dedicated test in this session (see RESULT.md's "What's not done" section).
