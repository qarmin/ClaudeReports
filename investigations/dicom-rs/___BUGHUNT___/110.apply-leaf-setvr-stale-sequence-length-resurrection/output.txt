Note the mechanism: `header.len after items_mut() mutation` correctly shows `Length(Undefined)`
in both variants (the `DataElement::update_value` guard candidate 109 confirmed is doing its
job). But immediately after `apply(AttributeOp::new(seq_tag, AttributeAction::SetVr(VR::SQ)))`
on the very same tag, `header.len` flips back to the *pre-mutation* explicit length (`Length(20)`
for the 1-item input in push-growth, `Length(40)` for the 2-item input in remove-shrink) - the
stale value cached in `DataSetSequence`'s own private `length` field at parse time, resurrected by
`apply_leaf`'s `SetVr` arm calling `DataElement::new(header.tag, new_vr, value)`, which recomputes
`header.len` from `value.length()`. Writing that stale length verbatim
(`ExplicitLengthSqItemStrategy::NoChange`) produces a data set whose declared sequence length no
longer matches its actual encoded item content (2 items where the old length only covered 1, in
push-growth; 1 item's worth of bytes where the old length still claims 2, in remove-shrink) -
detected by round-tripping the writer's own output back through the crate's own real reader,
which fails to parse it at all in both variants.

Reproduced identically on 3/3 repeat runs each variant (deterministic, fixed input, no
randomness in this code path): same wire bytes, same header.len values, same error, same exit
code, every time.

Post-fix, `SetVr` no longer recomputes `header.len` from the sequence's vestigial private
`length` field - it keeps the length `Length::UNDEFINED` for `Value::Sequence`, which is always a
valid encoding, instead of trusting a field `items_mut()` never updates. Both variants now
round-trip correctly through the real writer and real reader with no corruption.
