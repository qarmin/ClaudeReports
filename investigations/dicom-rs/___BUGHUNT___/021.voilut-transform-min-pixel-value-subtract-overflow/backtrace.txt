This confirms the panic originates at pixeldata/src/transform.rs:238, inside
`VoiLutTransform::apply`, exactly as expected from the code-reading analysis:
`(value_rounded - self.lut.min_pixel_value) as usize` overflows i32 when
`value_rounded` is close to i32::MAX and `min_pixel_value` is negative.

Because the LUT table is filled with `rayon`'s `into_par_iter()` by default,
every worker thread independently computes the same out-of-range table index
and panics - hence the repeated "thread '<unnamed>' (PID) panicked" lines
when running with several CPU cores. Only one panic is needed to fail the
`.collect::<Result<Vec<_>, _>>()` call and abort image conversion.

=== Additional signal gathered during investigation (not part of the
    self-contained repro/justfile flow): a plain release build with
    overflow-checks left at their Cargo default (off) does NOT panic - the
    subtraction silently wraps in two's-complement arithmetic. In this
    specific crafted input the wrapped index still lands out of the LUT
    data's bounds, so `.get(...).unwrap_or(self.lut.data.last().unwrap())`
    happens to fall back to the last table entry (pixel value 255) - the
    same value the fixed code also happens to produce here. This does not
    mean the wraparound is harmless in general: for other (min_pixel_value,
    value_rounded) pairs, the wrapped index can land *inside* the table's
    bounds by coincidence, silently returning the wrong LUT entry instead of
    the correct one or a bounded fallback. The debug-reachable panic above
    is the reliably reproducible half of this bug; the silent-wrong-value
    half is real but was not independently reproduced with a concrete
    diverging pixel value in the time available. ===
