Approach 1: direct raw syscall, IORING_REGISTER_PROBE with a poisoned buffer
=============================================================================
$ gcc -o test test.c && ./test
io_uring_setup fd=3
PROBE ret=-1 errno=22 (Invalid argument)

(ret < 0, so the "buffer changed from poison" check branch in test.c was never reached - the
kernel rejected the call before it could have written anything through the `arg` pointer.)

Approach 2: direct raw syscall, IORING_REGISTER_PBUF_RING (prerequisite) + IORING_REGISTER_PBUF_STATUS
========================================================================================================
$ gcc -o test3 test3.c && ./test3
PBUF_RING register ret=0 errno=0 (Success)
PBUF_STATUS ret=-1 errno=22 (Invalid argument)
  status.head after call = 0xabababab (poison was 0xABABABAB)

(The prerequisite IORING_REGISTER_PBUF_RING call succeeds for real - bgid 42, 8 entries, real
mmap'd ring memory - so the ring/buffer-group machinery itself works on this kernel. The
subsequent PBUF_STATUS call still returns -EINVAL and status.head is provably untouched,
still exactly the poison pattern 0xABABABAB.)

Approach 3: sanity sweep to rule out "io_uring itself is sandboxed/blocked"
============================================================================
$ gcc -o test2 test2.c && ./test2
PERSONALITY ret=1 errno=0 (Success)
ENABLE_RINGS ret=-1 errno=77 (File descriptor in bad state)
BOGUS(999) ret=-1 errno=22 (Invalid argument)

(IORING_REGISTER_PERSONALITY succeeds for real (returns a fresh personality id, 1) and
IORING_REGISTER_ENABLE_RINGS gives a distinct, semantically-real error (EBADFD, because
IORING_SETUP_R_DISABLED was never set) - both prove io_uring_register as a syscall is NOT
blanket-blocked by a seccomp filter or similar in this container: real opcodes reach real kernel
logic and get real, opcode-specific answers. A genuinely bogus opcode (999) gets -EINVAL -
exactly the same code PROBE and PBUF_STATUS get.)
