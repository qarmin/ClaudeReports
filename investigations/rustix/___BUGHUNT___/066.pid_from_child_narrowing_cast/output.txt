=== Approach 2: cross-platform kernel/OS source ceilings for every target `src/pid.rs`'s module compiles on ===
(module gated `#[cfg(not(any(windows, target_os = "wasi")))]` in src/lib.rs:368 - Windows and WASI never compile this code)
- Linux:   include/linux/threads.h -> PID_MAX_LIMIT = 4 * 1024 * 1024 = 4194304 on 64-bit (sizeof(long) > 4);
           this container's own /proc/sys/kernel/pid_max already reads 4194304 and is read-only (cannot be
           raised further - this IS the kernel-enforced ceiling, not just today's configured value).
- FreeBSD: sys/sys/proc.h -> #define PID_MAX 99999
- macOS (xnu): bsd/sys/proc_internal.h -> #define PID_MAX 99999
- OpenBSD: sys/sys/proc.h -> #define PID_MAX 99999
- NetBSD:  sys/sys/proc.h -> #define PID_MAX 30000
- illumos: usr/src/uts/common/os/pid.c's pid_allocate() cycles a bounded [minpid, maxpid) pool
           (ASSERT(minpid <= mpid && mpid < maxpid); mpid wraps to minpid at maxpid), i.e. a bounded
           allocator, not the raw 32-bit range - consistent in shape with every other platform checked,
           though the exact numeric default/ceiling was not independently pinned down this session.
All of the above are many orders of magnitude below the 2^31 (2147483648) boundary at which
`child.id(): u32 as i32` would become non-positive.
