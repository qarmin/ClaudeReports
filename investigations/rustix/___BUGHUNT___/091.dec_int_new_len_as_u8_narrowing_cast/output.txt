=== Manual arithmetic check (BUF_LEN / len bound proof) ===
U64_MAX_STR_LEN = "18446744073709551615".len() = 20 (verified: python3 -c "print(len('18446744073709551615'))" -> 20)
I64_MAX_STR_LEN = "-9223372036854775808".len() = 20 (verified likewise)
BUF_LEN = U64_MAX_STR_LEN + 1 = 21

DecInt::new(i) loop trace:
  len starts at 1.
  Each loop iteration: len += 1, write one digit. Loop runs exactly `k` times, where `k` is the
  number of decimal digits in the unsigned magnitude of `i` (k in [1, 20] for every Integer impl,
  since all of them - i8/i16/i32/i64/u8/u16/u32/u64/isize/usize on 16/32/64-bit targets - fit in
  a 64-bit magnitude, and u64::MAX has exactly 20 digits).
  After the loop: len = 1 + k, so len in [2, 21].
  If is_neg: len += 1, so len in [3, 22] -- but is_neg can only be true together with the signed
  i64::MIN magnitude case, whose unsigned magnitude 9223372036854775808 has exactly k=19 digits,
  giving len = 1+19+1 = 21, not 22. (Any smaller-width signed type's MIN has strictly fewer digits,
  so len is correspondingly smaller.)
  Maximum achievable len over every Integer impl is therefore exactly 21 == BUF_LEN - the
  `len > BUF_LEN` guard (and its `unreachable_unchecked()`) is never actually exercised, and
  `len as u8` is always in [1, 21], nowhere near the u8::MAX (255) truncation point, and never 0
  (so `NonZeroU8::new(len as u8).unwrap()` never panics either).
