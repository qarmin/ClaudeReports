=== rs_reaper (the other half of the original candidate description) - NOT reproducible ===

Real FreeBSD kernel source for `reap_status()` (same file, same fetch):

    static int
    reap_status(struct thread *td, struct proc *p, void *data)
    {
            struct proc *reap, *p2, *first_p;
            ...
            reap = get_reaper_or_p(p);
            if (reap == p)
                    rs->rs_flags |= REAPER_STATUS_OWNED;
            if (reap == initproc)
                    rs->rs_flags |= REAPER_STATUS_REALINIT;
            rs->rs_reaper = reap->p_pid;
            ...
    }

    static struct proc *
    get_reaper_or_p(struct proc *p)
    {
            sx_assert(&proctree_lock, SX_LOCKED);
            return ((p->p_treeflag & P_TREE_REAPER) == 0 ? p->p_reaper : p);
    }

`reap` is always either `p` itself (a live, already-validated target process) or `p->p_reaper`
(every live process has a reaper - it defaults to/terminates at `initproc`, pid 1, never NULL).
`rs_reaper = reap->p_pid` is therefore always a real, positive (>= 1) pid for any process the
kernel can locate at all - there is no code path in `reap_status()` that ever assigns `rs_reaper`
to 0 or -1. The "spurious Err(RANGE) from a legitimately-reported 0/-1 `rs_reaper`" premise in the
original candidate description does not hold; `get_reaper_status`'s existing
`Pid::from_raw(raw.rs_reaper).ok_or(io::Errno::RANGE)?` is correct as written.
