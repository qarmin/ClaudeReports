=== Step 1: code reading - from_raw_unchecked vs from_raw_nonzero_unchecked ===

$ sed -n '213,257p' src/signal.rs

    /// Convert a raw signal number into a `Signal` without checks.
    ///
    /// # Safety
    ///
    /// `sig` must be a valid and non-zero signal number.
    /// ...
    pub const unsafe fn from_raw_unchecked(sig: i32) -> Self {
        Self::from_raw_nonzero_unchecked(NonZeroI32::new_unchecked(sig))
    }

    /// Convert a raw non-zero signal number into a `Signal` without checks.
    ///
    /// # Safety
    ///
    /// `sig` must be a valid signal number.
    /// ...
    pub const unsafe fn from_raw_nonzero_unchecked(sig: NonZeroI32) -> Self {
        Self(sig)
    }

Unlike candidate 057's `from_raw_nonzero_unchecked` (whose body is just `Self(sig)`, no internal
UB-capable primitive because `sig` is already a checked `NonZeroI32` by the time it's called),
`from_raw_unchecked` calls `NonZeroI32::new_unchecked(sig)` directly on a still-possibly-zero raw
`i32` - this is the same shape as candidate 035's confirmed-UB `Pid::from_raw_unchecked`, not
candidate 057's not-reproducible `Signal::from_raw_nonzero_unchecked`.

The call site under investigation, `src/event/kqueue.rs:124`:

    c::EVFILT_SIGNAL => EventFilter::Signal {
        // SAFETY: `EventFilter::new` requires a valid `Signal`.
        signal: unsafe { Signal::from_raw_unchecked(self.inner.ident as _) },
        times: self.inner.data as _,
    },

`self.inner.ident` is the raw `uintptr_t`/`intptr_t` field of a `kevent_t` struct as returned by a
real `kevent(2)` syscall - i.e. kernel-controlled data on the decode side, not validated at this
call site before being fed into the unsafe constructor.

=== Step 3: kernel source review - can a real kevent(2) ever report ident == 0 for a triggered EVFILT_SIGNAL event? ===

This step establishes whether the kernel-controlled `self.inner.ident` feeding this call site can
ever actually be 0 after a real kevent(2) wait call returns a *triggered* (not just registered)
EVFILT_SIGNAL event, on the two kqueue-capable OS families this code targets.

--- FreeBSD (github.com/freebsd/freebsd-src mirror of cgit.freebsd.org/src, sys/kern/kern_sig.c) ---

$ curl https://cgit.freebsd.org/src/plain/sys/kern/kern_sig.c
$ grep -n "filt_sig\|EVFILT_SIGNAL\|NOTE_SIGNAL" kern_sig.c

static int
filt_sigattach(struct knote *kn)
{
	struct proc *p = curproc;

	kn->kn_ptr.p_proc = p;
	kn->kn_flags |= EV_CLEAR;		/* automatically set */

	knlist_add(p->p_klist, kn, 0);

	return (0);
}
                                                        <- NOTE: no validation of kn->kn_id at all

static int
filt_signal(struct knote *kn, long hint)
{

	if (hint & NOTE_SIGNAL) {
		hint &= ~NOTE_SIGNAL;

		if (kn->kn_id == hint)
			kn->kn_data++;
	}
	return (kn->kn_data != 0);
}
                                  <- only becomes "ready" (f_event true) if a NOTE_SIGNAL|sig hint
                                     with sig == kn_id (the registered ident) is ever posted

The only call site that posts a NOTE_SIGNAL hint, tdsendsignal() (sys/kern/kern_sig.c):

int
tdsendsignal(struct proc *p, struct thread *td, int sig, ksiginfo_t *ksi)
{
	...
	if (!_SIG_VALID(sig))
		panic("%s(): invalid signal %d", __func__, sig);
	...
	KNOTE_LOCKED(p->p_klist, NOTE_SIGNAL | sig);
	...
}

$ grep -n "_SIG_VALID" sys/sys/_sigset.h
#define	_SIG_VALID(sig)	((sig) <= _SIG_MAXSIG && (sig) > 0)

=> tdsendsignal() *panics* (kernel panic, i.e. this path is definitionally unreachable in a
   functioning kernel) if ever called with sig <= 0, including sig == 0 - so `NOTE_SIGNAL | 0` is
   never posted through the normal, universal signal-delivery path.

$ grep -n "^kill(" -A 40 xnu_kern_sig.c | sed -n '1,40p'
kill(proc_t cp, struct kill_args *uap, __unused int32_t *retval)
{
	...
	if ((u_int)uap->signum >= NSIG) {
		return EINVAL;
	}
	...

			psignal(p, uap->signum);
		}

                       <- the kill(2) syscall's own "existence test" special case (POSIX
                          kill(pid, 0) semantics) explicitly skips calling psignal() at all when
                          signum == 0, so psignal_internal()/proc_knote(..., NOTE_SIGNAL | 0) is
                          never reached via this path either.

Conclusion: on both FreeBSD and macOS/XNU - the two kqueue-capable OS families actually checked -
signal number 0 is architecturally never delivered through the kernel's real signal-posting path
(a direct, structural consequence of POSIX's own kill(pid, 0) "no signal sent, existence/permission
test only" semantics, enforced in FreeBSD by an outright kernel panic on any other caller attempting
it, and in macOS/XNU by the kill(2) syscall never calling psignal() for signum == 0 in the first
place). Even though `filt_sigattach` on both platforms would readily accept *registering* a knote
with `ident == 0` for EVFILT_SIGNAL (no validation at attach time), such a knote's "ready" condition
(`kn_data != 0`, driven exclusively by NOTE_SIGNAL hints matching its ident) can structurally never
become true - so no real kevent(2) wait call can ever return a *triggered* EVFILT_SIGNAL event with
ident == 0, regardless of what registered it or how.
