2. libc crate's own `Padding<T>` type (src/types.rs in libc 0.2.189, the version this repo's
   Cargo.lock would resolve to via the `libc = "0.2.171"`/"0.2.182" constraints in Cargo.toml) -
   a transparent MaybeUninit<T> wrapper the libc maintainers use specifically for C struct fields
   whose contents "might be uninitialized" when returned from C:
====================================================================
//! Platform-agnostic support types.

#[cfg(feature = "extra_traits")]
use core::hash::Hash;
use core::mem::MaybeUninit;

use crate::prelude::*;

/// A transparent wrapper over `MaybeUninit<T>` to represent uninitialized padding
/// while providing `Default`.
// This is restricted to `Copy` types since that's a loose indicator that zeros is actually
// a valid bitpattern. There is no technical reason this is required, though, so it could be
// lifted in the future if it becomes a problem.
#[allow(dead_code)]
#[repr(transparent)]
#[derive(Clone, Copy)]
pub(crate) struct Padding<T: Copy>(MaybeUninit<T>);

impl<T: Copy> Default for Padding<T> {
    fn default() -> Self {
        Self(MaybeUninit::zeroed())
    }
}

impl<T: Copy> Padding<T> {
    /// Create a `Padding` initialized with the given value.
    #[allow(dead_code)]
    pub(crate) const fn new(val: T) -> Self {
        Self(MaybeUninit::new(val))
    }

Seminal rationale, libc issue #1453 "Wrap padding fields in Padding(MaybeUninit<T>)"
(https://github.com/rust-lang/libc/issues/1453), quoted verbatim:

  "libc uses integers and aggregates of integers for explicit padding byte fields. When these
  fields are returned from C, they might be uninitialized. We currently do not have any wording
  in the spec saying that an uninitialized integer is not instant undefined behavior, and there
  are proposals that define them to both be ok, and to actually be instant undefined behavior.
  These padding fields should use MaybeUninit<INT> instead."

   (https://github.com/vocho/openqnx, trunk/lib/c/1/tcgetattr.c - QNX 6.3.0's own libc, released

   caller's own (uninitialized, in rustix's case) buffer pointer straight into a `_devctl()` call

#include <devctl.h>
#include <sys/dcmd_chr.h>
#include <errno.h>

int tcgetattr(int fd, struct termios *termios_p) {
	return _devctl(fd, DCMD_CHR_TCGETATTR, termios_p, sizeof *termios_p, _DEVCTL_FLAG_NORETVAL | _DEVCTL_FLAG_NOTTY);
}

5. QNX's own official documentation (qnx.com, versions 6.4.1 through 7.1, consistent across all
   of them) confirms the struct layout and names the field "reserved[3]", type `uint32_t`/
   `_Uint32t`, sitting between `c_cc[NCCS]` and `c_ispeed`/`c_ospeed` - matching rustix's
   `Termios::__reserved` placement exactly. Source (fetched 2026-10-01):
   https://www.qnx.com/developers/docs/7.1/com.qnx.doc.neutrino.lib_ref/topic/t/termios.html
   https://github.com/vocho/openqnx/blob/master/trunk/lib/c/public/termios.h
   No official QNX documentation page states whether `tcgetattr()` writes a defined value into
   this field - the field is documented only as present for ABI/future-extension purposes, with
   no stated contract either way.
