introduced in c2699e36 "Add a `rustix::pty` module. (#673)" and has not changed shape since.

--- Approach 3: audit the real upstream XNU kernel source that implements TIOCPTYGNAME, to check
whether the "kernel might not NUL-terminate" premise is realizable on any currently-known real
macOS kernel ---
Fetched (read-only, via raw.githubusercontent.com, apple-oss-distributions/xnu, branch "main") the
three kernel files that implement every registered pty/ptmx ioctl handler on real macOS:

$ curl -s https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/sys/ttycom.h | grep -n TIOCPTYGNAME
181:#define TIOCPTYGNAME    _IOC(IOC_OUT, 't', 83, 128)     /* ptsname(3) */

-> Confirms the encoded ioctl size is 128 bytes, matching rustix's own stack buffer - this is the
*same* 128 both sides agree on, not a mismatch.

$ curl -s https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/kern/tty_dev.c | sed -n '1113,1122p'
        case TIOCPTYGNAME:      /* ptsname(3) */
                /*
                 * Report the name of the replica device in *data
                 * (128 bytes max.).  Use the same template string
                 * used for calling devfs_make_node() to create it.
                 */
                pty_get_name(dev, data, 128);
                error = 0;
                goto out;

-> The generic ioctl dispatcher (shared by both the legacy /dev/pty* driver and the modern
/dev/ptmx driver - every registered `tty_dev_t`) calls `pty_get_name(dev, data, 128)` with a
hardcoded size of 128, identical to the ioctl's own encoded size above.

$ curl -s https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/kern/tty_ptmx.c | sed -n '453,456p'
ptmx_get_name(int minor, char *buffer, size_t size)
{
        return snprintf(buffer, size, "/dev/" PTSD_TEMPLATE, minor);
}

$ curl -s https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/kern/tty_pty.c | sed -n '135,141p'
static int
pty_get_name(int minor, char *buffer, size_t size)
{
        return snprintf(buffer, size, "/dev/tty%c%x",
                   START_CHAR + (minor / HEX_BASE),
                   minor % HEX_BASE);
}

-> Both of the only two `name()` callbacks ever registered in the current XNU source
(the modern /dev/ptmx driver and the legacy /dev/pty* driver - there is no third) write via
`snprintf(buffer, size, ...)`. `snprintf`'s C standard contract guarantees NUL-termination
within the first `size` bytes whenever `size > 0` (it either fits and NUL-terminates, or
truncates and still NUL-terminates at `size - 1`) - it can never leave `buffer` without a NUL
within the first 128 bytes. The device names themselves ("/dev/ttyp0".."/dev/ttysXX" style,
a handful of bytes) are also nowhere near the 128-byte limit, so truncation itself never
actually occurs in practice either.

=> Conclusion: on every currently known real macOS kernel implementation, the exact mechanism the
candidate worried about (kernel ioctl handler leaving the 128-byte buffer without a NUL) cannot
occur - it's ruled out structurally by `snprintf`'s own safety contract in the only two code paths
that have ever implemented this ioctl. The candidate's own hedged premise ("kernel bug, future ABI
change, reused ioctl number on a different BSD-flavored kernel") is explicitly speculative, and no
real second participant (a real macOS kernel, real hardware, or a working emulator/Darling) exists
in this environment to attempt to falsify that conclusion empirically rather than by source
reading.
