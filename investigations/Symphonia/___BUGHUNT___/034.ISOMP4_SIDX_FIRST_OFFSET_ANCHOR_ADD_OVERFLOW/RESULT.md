# ISOMP4_SIDX_FIRST_OFFSET_ANCHOR_ADD_OVERFLOW

`SidxAtom::read` (`symphonia-format-isomp4/src/atoms/sidx.rs:58-59`) computes the segment index's
`first_offset` as `anchor + <first_offset field read straight out of the file>` with a plain `+`:

```rust
0 => (u64::from(it.read_u32()?), anchor + u64::from(it.read_u32()?)),
1 => (it.read_u64()?, anchor + it.read_u64()?),
```

`first_offset` is an entirely unvalidated 32-/64-bit field. `AtomHeader::read` explicitly guards
its own `atom_pos + atom_len` overflow (`atoms/mod.rs:554`), so `anchor` itself cannot overflow -
but nothing guards this second addition. Same bug class as candidate 016 (FLAC SEEKTABLE
`first_frame_offset + SeekPoint::byte_offset`) at a different site; distinct from candidate 018's
ruled-out midpoint sites, because the operand here is a raw file field rather than a real stream
position. `HEURISTICS.md`: "arithmetic on offsets derived from input".

Two approaches were enough (a signal appeared on the first real one) - the 3-approach soft cap was
not needed. No miri/ASAN/fuzzing: per `___BUGHUNT___/README.md` this is pure safe Rust, and Rust's
own checked arithmetic is the right instrument for this class.

## Status

**Confirmed**. Reproduces 5/5 runs per crafted file (10/10 across both), deterministic, in any
build with `overflow-checks = true` (Rust's default for the `dev` profile; enabled explicitly in
the repro's release profile). Does **not** manifest with overflow checks off - there the addition
wraps silently and the wrapped value is never used.

**Fully reproducible**: **Yes**. Both crafted files are real, structurally-valid ISO-BMFF byte
streams (a normal `ftyp` atom followed by a single `sidx` atom, generated by
`repro/gen_mp4.py` with no hand-poked internal state), handed to the real public
`IsoMp4Reader::try_new` entry point - exactly how a player opens an MP4. Per `CONFIRMATION.md`
section 11, a malformed file handed to a parser's real public entry point *is* the genuine
external input; there is no second participant being stood in for. `just test` runs the whole
before/apply/after cycle against a fresh clone of the upstream repo at `base_commit`.

## Class

crash (checked-arithmetic overflow panic, `overflow-checks = true` builds only)

## Root cause

`SidxAtom::read` computes the segment index's anchor-relative `first_offset` as an absolute file
position by adding the `sidx` atom's own end position (`anchor`, "the first byte after this atom")
to the `first_offset` field read verbatim from the stream. The field is a plain `u32` (version 0)
or `u64` (version 1) with no range check of any kind - not against the stream length, not against
`u64::MAX - anchor`. The surrounding code does validate other untrusted `sidx` fields (`timescale`
is rejected when zero, `total_duration` is accumulated with `checked_add` and a dedicated
"total duration overflow" decode error, `AtomHeader::read` refuses an atom whose end position
would exceed `u64::MAX`), so this one addition is the odd one out rather than a deliberate
trusted-input assumption.

Two independent ways to make the sum exceed `u64::MAX`, both demonstrated:

- version 1 (sidx.rs:59): `first_offset` is a full `u64`, so `u64::MAX` overflows for *any*
  `anchor`, and `anchor` is always at least 8. This needs nothing unusual of the container - the
  `sidx` atom's declared size matches the real file size and the stream is an ordinary seekable
  file.
- version 0 (sidx.rs:58): `first_offset` is only 32 bits, so `anchor` has to be pushed near
  `u64::MAX`. That is reachable on an **unseekable** source: `AtomIterator::new` is given
  `len = None`, `next_header`'s `child_end > parent_end` check is therefore skipped entirely, and
  a 64-bit atom size of `u64::MAX - atom_pos` (the largest `AtomHeader::read`'s own guard allows)
  makes `anchor` exactly `u64::MAX`, so a `first_offset` of 1 suffices.

The resulting `SidxAtom::first_offset` is never read anywhere in the crate (the struct is
`#[allow(dead_code)]`), so with overflow checks disabled the wrapped value is harmless - the
finding is the panic in `overflow-checks = true` builds, on a path any caller reaches simply by
opening an untrusted MP4.

## The fix

`patch.diff` reads the version-dependent `first_offset` field into a local without adding to it,
then folds in the anchor with `checked_add`, surfacing an ordinary
`Error::DecodeError("isomp4 (sidx): first offset overflow")` instead of panicking. This mirrors
exactly what the same function already does 20 lines below for `total_duration`, and rejecting the
atom is the correct semantics: a `first_offset` whose absolute position does not fit in a `u64`
cannot describe a byte position in any real stream.

Per `CONFIRMATION.md` section 7 the fix was checked against more than the single input that first
triggered it: both version arms are exercised by separate files coming at the addition from
opposite sides (a maximal `first_offset` with a small anchor, and a minimal `first_offset` with a
maximal anchor via an unseekable stream), plus a control file with a plausible `first_offset` that
must keep behaving exactly as before.

Before the patch: both crafted files panic (5/5 runs each). After: both return
`Err(malformed stream: isomp4 (sidx): first offset overflow)`, 5/5 runs each, and the control file
still returns the unchanged `Err(unsupported feature: isomp4: missing moov atom)`. See
`output.txt` for the real `just test` output (fresh upstream clone, before + after) and the
pre-patch backtrace.

- Project test suite (`cargo test --workspace`): **106 passed, 0 failed** before the patch,
  **106 passed, 0 failed** after - identical, no new failures. `cargo +nightly fmt -p
  symphonia-format-isomp4 -- --check` reports no diff for `sidx.rs` after the patch.

## What's not done / open questions

- The `sidx` fix is a rejection, not a clamp. If `first_offset` ever starts being *used* (it is
  currently dead), a maintainer may prefer to keep the atom and clamp/ignore the offset instead of
  failing the whole read - the parse-time decode error chosen here matches the neighbouring
  `timescale is zero` / `total duration overflow` handling, but that is a project-style decision.
- The unseekable-stream gap this candidate surfaced is broader than `sidx`: when
  `AtomIterator::len` is `None`, `next_header` applies **no** bound at all to a top-level atom's
  declared size, so any other atom reader that derives arithmetic from `header.pos() + size` can be
  handed an `anchor` of up to `u64::MAX`. Only `sidx.rs` was audited for this; a sweep of the other
  `atoms/*.rs` readers for `header.pos()`/`header.end()`/`data_size()`-derived arithmetic was not
  done this session - reported back as a new suspect for `IDEAS.md`.
- Whether the existing `demux_isomp4` cargo-fuzz target could find this was not tested.
  libfuzzer-sys builds in release with overflow checks off by default, so as written it almost
  certainly cannot - it would need `RUSTFLAGS="-C overflow-checks=on"` (or `cargo fuzz build -O -d`)
  to see this class of bug at all, which is worth noting for any future campaign on this crate.
- Other unchecked offset arithmetic in `symphonia-format-isomp4` (candidates already queued in
  `IDEAS.md` for `traf.rs`/`stream.rs`) was not touched here - one bug per candidate folder.
