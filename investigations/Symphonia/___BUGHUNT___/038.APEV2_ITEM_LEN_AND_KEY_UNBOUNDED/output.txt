Reading of the numbers above:
- `item-len-max` and `key-no-nul` at a small constant multiple of the file size (the
  multiple is the doubling-realloc transient, not the declared length) means the 32-bit
  item length and the uncapped key loop are both bounded by how many bytes the stream
  actually has, not by the declared 32-bit value:
  `ReadBytes::read_boxed_slice_exact` grows progressively (4 MiB first, then doubling)
  with `try_reserve_exact`, so a 4 GiB claim behind a short file fails with a clean error
  instead of reserving 4 GiB.
- `num-items-past-extent` and `num-items-honest` costing the same means the missing
  num_items-vs-size cross-check does not change the resource cost: a tag can declare the
  same item stream honestly and get the same result.
- `id3v2-baseline` in the same ballpark means the per-byte amplification is a property of
  storing one `Tag` per parsed item/frame, shared with the crate's other standalone
  reader, not an APE-specific defect.
